# 长期记忆系统部署与评测指南

> 2026-10-09 更新：事件／重要一次性计划、时间精度与消息级来源、共享提取与维护规则、英文评测回答及诊断导出，见 [记忆事件与时间改进及复测说明](记忆事件与时间改进及复测说明.md)。上线需先执行 0008；本轮尚未执行真实迁移或付费复测。

本文回答两个问题:**怎么把它上线**(部署、配置、自检、运维、回滚),**怎么验它**(离线评测怎么跑、口径怎么读、哪些还没验)。系统为什么这么设计、各模块怎么协作,见《长期记忆系统技术方案》(下称「技术方案」);表结构口径见 `backend/migrations/README.md` 的 0004 / 0005 / 0006 各节。

读者:负责部署与运维的人、执行评测的人。文中命令默认在仓库根目录执行,后端命令的工作目录是 `backend/`。

## 1. 上线前需要什么

### 1.1 依赖一览(哪些缺了就不能跑)

| 依赖 | 角色 | 缺了会怎样 |
| --- | --- | --- |
| **MySQL**(`MYSQL_URL`,与计量、认证同一个库) | **事实源**:记忆、任务、审计、代次都在这里 | 记忆接口返回 503 并说明缺什么;**聊天不受影响**(记忆是软依赖,绝不假装「你没有记忆」) |
| **Qdrant**(`QDRANT_URL` + `MEMORY_COLLECTION`) | 可重建索引(稠密召回一路) | 记忆还在(MySQL 权威),检索退化成只有 BM25,并在结果里记降级 |
| **Redis**(`REDIS_URL`) | 缓存:向量化结果(与知识库共用一套);计算锁 | 每次要向量化时多花一次调用,功能不受影响 |
| **LLM 聊天模型**(`LLM_*`,与问答同一个) | 提取事实、维护决策 | 新记忆不再产生(任务失败可重试);回答不带新记忆 |
| **Embeddings**(`EMBEDDINGS_*`) | 索引与查询向量化 | 索引写不进去(行留 `pending` 自愈);检索退化 |
| **Rerank**(`RERANK_*`,可选) | 融合后重排 | 不配置就按 RRF 顺序取 top_k,结果里有一条配置说明;不是故障 |

没有引入任何新的基础设施依赖:就是上面这套既有组件。没有 SQLite、ES、消息队列,没有图数据库。

### 1.2 表结构:手工依次执行 0004 + 0005 + 0006

应用启动**不建表、不跑迁移框架**。先执行迁移,再让带长期记忆的代码上线:

```sh
mysql --default-character-set=utf8mb4 -h <host> -u qa_migrate -p qa_agent_dev  < backend/migrations/0004_memory_tables.up.sql
mysql --default-character-set=utf8mb4 -h <host> -u qa_migrate -p qa_agent_dev  < backend/migrations/0005_memory_scope_fencing_index_ops.up.sql
mysql --default-character-set=utf8mb4 -h <host> -u qa_migrate -p qa_agent_dev < backend/migrations/0006_memory_scope_state_history.up.sql
mysql --default-character-set=utf8mb4 -h <host> -u qa_migrate -p qa_agent_prod < backend/migrations/0004_memory_tables.up.sql
mysql --default-character-set=utf8mb4 -h <host> -u qa_migrate -p qa_agent_prod < backend/migrations/0005_memory_scope_fencing_index_ops.up.sql
mysql --default-character-set=utf8mb4 -h <host> -u qa_migrate -p qa_agent_prod < backend/migrations/0006_memory_scope_state_history.up.sql
```

- `0004` 建四张表:`memory_items` / `memory_history` / `memory_jobs` / `memory_user_state`;
- `0005` 是同一组表的**增量**:`memory_items` / `memory_jobs` 各加 `scope`(作用域),
  `memory_jobs` 再加认领凭证与阶段结果(`claim_token` / `stages` / `outcome` / `committed_at`)、
  `turn_id`,`memory_items` 再加版本化索引标记(`meta_version` / `indexed_revision` /
  `indexed_meta_version`)与 `kind` / `event_time` / `generation`,另建两张新表
  `memory_sources`(记忆 ↔ 来源轮次)与 `memory_ops`(清理台账)。
  字段口径见技术方案 §4 与 `backend/migrations/README.md` 的 0005 一节。
- **顺序不能反**:0005 依赖 0004 建的表。已经跑过 0004 的库依次执行 **0005、0006**；已执行 0005 的库只执行 0006 即可(增量迁移,不需要重建,
  也不会动已有数据)。
- **为什么不是改 0004**:已经执行过 0004 的库不会重跑它,改旧脚本等于让那些库永远升不上来。
  所以新增量迁移,并同步更新回滚脚本。
- `--default-character-set=utf8mb4` 不能省(列注释是中文)。
- 重复执行会报 `1050 table already exists` / `1060 duplicate column name`(故意的,没有 `IF NOT EXISTS`)。
- 反向顺序也能活(缺表期间只有记忆接口报错),但没必要:先迁移,零窗口。
- 执行完把 `backend/migrations/README.md` 底部「部署记录」表里对应迁移的「未应用」改成实际状态。
- 回滚:先 `0006_*.down.sql`，再 `0005_*.down.sql`、`0004_*.down.sql`,**会连记忆与审计一起删**;执行前先让新版代码下线。
  Qdrant 集合不随它们清理(见 §8)。

### 1.3 运行账号授权(只有 DML)

应用账号 `qa_agent` 对记忆这六张表只需要 `SELECT, INSERT, UPDATE, DELETE`——建表是迁移账号 `qa_migrate` 的事。若这个库之前只授过 `SELECT`,写入会报 `1142 ... command denied`;而且它会盖住 `1146 ... doesn't exist`(MySQL 在 INSERT 路径上先查权限、后查表)。补齐语句:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON `qa_agent_dev`.*  TO `qa_agent`@`%`;
GRANT SELECT, INSERT, UPDATE, DELETE ON `qa_agent_prod`.* TO `qa_agent`@`%`;
```

### 1.4 配置项

全部配置在 `backend/.env`(模板 `backend/.env.example`,第 135 行起是记忆块)。最小可用配置:MySQL 已配 + `MEMORY_ENABLED=true`,其余用默认值即可。关键项分四组:

**开关组(任何开关都不删数据):**

| 变量 | 默认 | 语义 |
| --- | --- | --- |
| `MEMORY_ENABLED` | `true` | 总开关。false:登记任务、检索、管理接口全部安静地不做(聊天照常) |
| `MEMORY_WRITE_ENABLED` | `true` | false:**暂停自动写入**——不登记新任务、worker 不认领(队列原样留着);用户手添/编辑/删除**不受影响**;索引重放照跑(派生数据维护) |
| `MEMORY_SEARCH_ENABLED` | `true` | false:回答时不再注入记忆,也省掉每轮检索的向量化调用;「我的记忆」页里用户主动检索照常 |
| `MEMORY_MAINTENANCE_ENABLED` | `true` | false:退回「只新增 + 正文去重」,不改不删已有记忆(更便宜);属于显式降级,结果里会带说明 |
| `MEMORY_WORKER_ENABLED` | `true` | 后台提取线程。false:完全没有自动记忆,手动增删改查与检索仍在 |

**worker 组:** `MEMORY_WORKER_INTERVAL_SECONDS=5`(空轮询间隔)、`MEMORY_WORKER_TICK_LIMIT=3`(每轮最多几个任务,≤0 = 不限但有硬上限)、`MEMORY_WORKER_INDEX_BATCH=50`(空闲轮补索引的批大小)、`MEMORY_JOB_MAX_ATTEMPTS=3`、`MEMORY_JOB_BACKOFF_SECONDS=30`、`MEMORY_JOB_LEASE_SECONDS=300`(**必须大于一次提取的最长耗时**)。

**续租 / 对账 / 清理组(可靠性相关,改动前先读技术方案 §5.2、§8.1):**

| 变量 | 默认 | 语义 |
| --- | --- | --- |
| `MEMORY_JOB_RENEW_SECONDS` | `30` | 执行期间的续租间隔(实际取它与「租约的 1/3」中较小者)。**必须明显小于租约时长**;数据库抖动只是「这次没续上」,不算失去租约 |
| `MEMORY_WORKER_DRIFT_SECONDS` | `300` | 索引对账间隔:分页核验每条当前点及 payload，另登记孤儿和旧版本清理 |
| `MEMORY_WORKER_INDEX_REPAIR` | `true` | 对账发现漂移时是否自动选择性修复索引标记。false = **连周期性对账本身也不跑**(核验与登记孤儿一并停,不只是不修),只在排查 Qdrant 时临时关;不建议常关:那是唯一能发现「标记说已同步、点却不在集合里」的自动路径 |
| `MEMORY_WORKER_OPS_BATCH` | `20` | 一轮最多做掉几条清理台账 |
| `MEMORY_OP_MAX_ATTEMPTS` | `8` | 清理台账重试上限;**用尽落 `failed`,状态页显示「清理失败」,这时不会再有地方自动重试** |
| `MEMORY_OP_BACKOFF_SECONDS` | `30` | 清理台账重试退避基数 |

**检索组:** `MEMORY_VECTOR_K` / `MEMORY_BM25_K` / `MEMORY_RERANK_K` / `MEMORY_TOP_K`(四个数分开配,不要互相推导)、`MEMORY_VECTOR_OVERSAMPLE`、`MEMORY_RRF_K=60`、`MEMORY_CONTEXT_CHARS=2000`、`MEMORY_BM25_CORPUS_LIMIT=1000`、维护侧 `MEMORY_MAINTENANCE_*` 四个。公式与调参动机见技术方案 §6。

**重排组(`RERANK_*`,独立于 LLM/Embeddings):**

| 变量 | 说明 |
| --- | --- |
| `RERANK_ENABLED` | 默认 `false`(不配置就不重排,不是故障) |
| `RERANK_MODEL` / `RERANK_API_URL` / `RERANK_API_KEY` | 阿里云百炼 text-rerank 一类的独立接口;未配置时功能照跑、只在结果里记一条说明 |
| `RERANK_TIMEOUT_SECONDS` | 默认 15 |
| `MEMORY_RERANK_MAX_DOCS` / `MEMORY_RERANK_MAX_CHARS` | 单次重排输入上限(超出按融合顺序截断并记降级) |
| `MEMORY_RERANK_INSTRUCT` | **仅维护决策**用的排序说明(英文短句);回答检索留空,用供应商默认的问答检索提示 |

`MEMORY_COLLECTION`(默认 `user_memory`)必须与知识库 `QDRANT_COLLECTION` 分开——记忆集合是可整库重建的,别和知识库共用。

## 2. 部署步骤(按顺序)

1. **迁移**:执行 §1.2 的 0004(**首次上线才需要**)与 0005、0006(开发库、生产库各一次,顺序不能反),更新 `migrations/README.md` 部署记录。
2. **配 `.env`**:至少 `MEMORY_ENABLED=true` + 已有的 `MYSQL_URL`;需要重排就填 `RERANK_*`。改了 `requirements.txt` 才需要 `bash run.sh --deps`(记忆模块没有引入新依赖)。
3. **发版/重启**:worker 由应用 lifespan 启动(`app/main.py`),只在 `MEMORY_WORKER_ENABLED=true` **且** 配了库时真正起线程;启动失败不影响应用。
4. **自检**:按 §3 走一遍。

多进程部署(uvicorn 多 worker / 多台)是安全的:任务认领是带条件的 UPDATE,同一任务只有一个进程领得到;同一用户同时只有一个任务在跑(认领时避开租约未过期的用户)。每台机器都会起自己的后台线程,互相靠租约协调。

## 3. 自检清单(上线后 5 分钟)

1. **看启动日志**:确认没有「记忆」相关的 error;worker 起没起可以在下一步看。
2. **看状态接口**(普通用户登录后带 token):
   `GET /api/v1/memory/status` —— 逐项核对:
   - `enabled` / `configured` 都是 true(configured=false 说明库没配上);
   - `write_enabled` / `search_enabled` / `maintenance_enabled` 与 `.env` 一致;
   - `worker_running` 是 true;
   - `items=0`、`index_pending=0`(新用户);
   - `cleanup_pending=0`、`cleanup_failed=0`(清理台账;非 0 看 §5 的「清理失败」一行)。
3. **看界面**:前端「我的记忆」页能打开,开关状态与上面一致、没有报错条。
4. **造一条记忆**(用**测试账号**,别拿真实敏感内容):
   - 在对话里说一句「我以后都用 Markdown 写实验记录」→ 等一个 worker 周期(默认 5 秒,加提取与维护耗时,通常十几秒内);
   - 回到「我的记忆」页刷新:出现这条记忆,来源是会话提取;
   - `GET /memory/status` 的 `items ≥ 1`、`index_pending=0`;Qdrant 里 `user_memory` 集合的 `count` 与之一致。
5. **验证隔离**:换第二个测试账号登录,「我的记忆」里**看不到**第一个账号的任何内容;`GET /api/v1/memory?q=Markdown` 返回空。
6. **验证删干净**:第二个账号说一句、然后在记忆页点「彻底删除…」;`items` 回到 0,再问同一句话,回答不再引用它(注意:聊天记录不随之删除,之后的交流会重新提取同样的事实——这是既定语义)。

## 4. 日常运维动作

| 想做什么 | 怎么做 | 注意 |
| --- | --- | --- |
| 暂停自动写入(降本 / 活动期间停) | `MEMORY_WRITE_ENABLED=false` 重启 | 队列原样留着,开回来继续;手添/编辑/删除不受影响;索引重放照跑 |
| 暂停回答时检索 | `MEMORY_SEARCH_ENABLED=false` 重启 | 省掉每轮向量化;管理页主动检索仍在 |
| 只保新增、停维护决策 | `MEMORY_MAINTENANCE_ENABLED=false` 重启 | 显式降级:不更新、不删除旧记忆,结果里带说明 |
| 补索引(单用户) | 「我的记忆」页的「补索引(N)」按钮 → `POST /api/v1/memory/reindex` | 用户自助。返回里 `indexed` 是重算了向量的条数,`payload_only` 是「正文没变、只更新元数据」的条数(**这几条不该产生 Embedding 调用**,若 `payload_only` 很大而 `indexed=0`,说明这批只是元数据变了) |
| 补索引(批量/兜底) | 什么都不用做:worker 空闲轮自动重放 | embedding 端点持续不可用时按 60s→120s→… 最长 15 分钟退避,不反复打付费端点;worker 还会按 `MEMORY_WORKER_DRIFT_SECONDS` 对账(逐条核验 → 标记不一致的当前版本 → 补写) |
| 彻底清除某用户记忆 | 用户自己在记忆页点「彻底删除…」(`DELETE /api/v1/memory?confirm=true`) | 只清该用户;Qdrant 侧同步删;聊天记录与账号不动。**返回里的 `cleanup=pending` 表示向量还没清完**,台账会由 worker 接着重试 —— 不要据此重跑删除(幂等但没必要) |
| 处理「清理失败」 | 看 `GET /api/v1/memory/status` 的 `cleanup_failed`;库里 `memory_ops` 里 `status='failed'` 的行有 `last_error` | 这只影响**派生索引**残留:记忆事实早已删掉。修好 Qdrant(或删掉集合重建)后,把该行 `status` 改回 `pending`、`next_run_at` 置当前时间,worker 会再做一次;`purge_user` 类操作也可靠「彻底删除」重跑一次(按新代次重新登记) |
| 清 Redis 里的向量化缓存 | 按缓存前缀批量删;或 `EMBEDDINGS_VERSION` +1 | 键是「模型口径 + 正文摘要」的哈希、值是向量,**不含正文**,缓存不是记忆的第二份副本;**用户「彻底清除」不清缓存**(技术方案 §8.2);改版本号会让知识库缓存一并失效,要权衡 |
| 换 embedding 模型 / 维度 | 四步:改 `.env`(`EMBEDDINGS_MODEL`/`EMBEDDINGS_DIM`/`EMBEDDINGS_VERSION`)→ 重建集合 → 重启 → 补索引 | 详见技术方案 §10;旧向量一并作废,`embedding_version()` 变了,Gdrant 命中会因版本不符被 MySQL 校验拦下,不会串号 |
| 关掉整个功能 | `MEMORY_ENABLED=false` 重启 | 数据全留着;再开回来一切照旧 |

## 5. 故障排查

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 记忆页报 503 | `MYSQL_URL` 没配 / 库不可达 / 0004、0005、0006 没执行(1146) | 按提示补;权限类错误先看是不是只授了 `SELECT`(1142) |
| 聊天半天不产生记忆 | ① `MEMORY_ENABLED`/`MEMORY_WRITE_ENABLED` 关了 ② `MEMORY_WORKER_ENABLED` 关了或 `worker_running=false` ③ LLM 提取一直失败(任务 `last_error` 只记类名或我们自己的说明)④ 端点不支持 JSON 模式导致结构校验反复失败 | 依次排查;④ 可设 `MEMORY_LLM_JSON_MODE=false`,结构校验与有限重试照常工作 |
| `index_pending` 不归零 | embedding 端点不可用 / 维度与集合不一致 | 维度不一致会在日志里明确报「需要显式重建集合」;端点不可用等自动重放 |
| 检索结果有条「降级」说明 | 未配重排(`RERANK_ENABLED=false`)/ 重排超时回退 RRF / 向量路不可用只剩 BM25 / BM25 语料超上限 | **说明不是故障**,按说明判断要不要处理 |
| 任务停在 `failed` 终态 | 结构错误、payload 为空、用户清除后作废 —— 这些重试无意义,故意不重试 | 看 `last_error`;库里 `memory_jobs` 可查(该表不存对话正文,终态时 `payload` 清成 `{}`) |
| 队列一直堆积 | worker 被关 / 上一进程被 kill 后租约未到期 | 租约 300 秒过期后自动放回重跑;进程活着但队列不动,先查 `worker_running` |
| `cleanup_failed` 不为 0 | 清理台账重试用尽(通常 Qdrant 长时间不可达) | **记忆事实已经删掉了**,这只是向量残留;修好 Qdrant 后按 §4 「处理「清理失败」」重置那一行 |
| 日志里出现「租约已不属于本次认领」 | 一次执行超过了租约时长且续租失败,任务被另一个执行者接管 | 这次执行的写入**会被 fencing 拦下、一个字都不会落库**(可放心);要减少发生:确认 `MEMORY_JOB_LEASE_SECONDS` 大于一次提取的最长耗时、`MEMORY_JOB_RENEW_SECONDS` 明显更小 |
| 日志里出现「索引对账发现漂移」 | 逐条核验发现当前索引点缺失或 payload 不一致 | 会自动选择性清除不匹配快照的同步标记并补写;反复出现要查 Qdrant 的持久化与容量 |
| 日志里出现「记忆索引发布后清理失败」 | 索引点**已经发布**,只是发布后的复核 / 登记 / 清旧版本点那几步当场失败(通常是 MySQL 或 Qdrant 抖动) | 不是索引写入失败:这条记忆的索引已生效、接口照常返回,`deferred` 也不会被它污染。已登记进台账的操作由 worker 重试;连登记都没做成的(库也不可用)由周期对账发现并补登,处置同 §4 「处理「清理失败」」 |
| 同一用户的记忆像是被写了两遍 | 维护决策被并发跑过(旧版本没有同用户串行) | 现在认领阶段就按代次行锁串行;**先确认版本**;查 `memory_history` 里同一时刻的 ADD 行 |
| 换了模型后检索突然变差 | 索引还是旧模型的向量 | 走 §4 「换 embedding 模型」四步 |

**排查时绝不要**:把 `MEMORY_*` 正文、对话内容、`.env` 内容贴到工单 / 日志 / 聊天里。日志口径就是为此设计的——记忆的正文从不进日志,失败原因只记类名。

## 6. 离线评测指南(技术方案 §14 的落地)

### 6.1 这个评测做什么、不做什么

**做**:在**可隔离、可清除、可复现**的前提下,量化「长期记忆」相对「无记忆」与「全文历史」两种基线在问答上的差异,并把检索证据与调用花费一起导出,供人判断。

**不做**(明确不宣称):

- **不自动跑大评测**。仓库只提供脚本、样本与文档;跑不跑、跑多大由人决定。
- **不宣称与 Mem0 等价,也不宣称复现其论文结果**。参考的只是设计思路(技术方案 §2 有 Mem0 v2.2.1 / Apache-2.0 的说明),数据与实现都不同。
- **不宣称指标能直接比大小**。三种模式用同一批问题、同一模型、同一版本的代码与参数(manifest 固定),但这不是公开基准。
- **功能测试不碰真实付费模型**;评测脚本**会**产生真实付费调用(见 §6.4 的费用口径),所以默认不跑。

### 6.2 隔离设计(为什么可以放心跑)

| 隔离点 | 做法 |
| --- | --- |
| 作用域维度(**主隔离**) | 每次 run 一个 `scope = eval:<run-id>`:记忆行 / 任务行 / 清理台账 / 来源关联都带这一列,且**认领、补索引、清理、清除、检索全部按它过滤**。评测 Worker 只认自己那一份,正式 Worker 领不到评测任务(反之亦然)—— 隔离落在 SQL 与向量过滤条件里,不靠「运行时记得别开正式 Worker」 |
| 用户维度 | run-id 经 UUIDv5 派生**专用 user_id**(`uuid5(命名空间, "memory-eval:{run-id}")`),与任何真实账号不可能撞;数据集里还可以给每条会话一个 `subject`(多主体场景),同一 run 内按 subject 再分用户 |
| 索引维度 | 与正式数据**同一个 Qdrant 集合**,但每个点的 payload 带 `scope`,检索/删点都按它过滤。不再另起集合:切集合要改进程级全局配置(`memory_collection`),那本身就会在切换窗口里写错地方 |
| run-id 校验 | run-id 既进 `scope` 又进导出文件名,所以**先正则校验再用**(字母 / 数字 / `.` `_` `-`,首字符必须是字母或数字,最长 49 字符;空值直接拒绝——空 run-id 派生的 scope 会与正式数据(`''`)撞上) |
| 输出维度 | 结果写到 `backend/data/eval/runs/<run-id>/`(已被 gitignore),不写生产目录 |
| 构建阶段 | 构建记忆时只喂对话,**开场先断言任何问题文本都没出现在构建输入里**(`assert_no_leak`);构建阶段不读答案,也不读「未来」的对话轮次 |
| 清理 | `purge` 按 `(用户, scope)` 清:记忆行 / 任务行 / 审计正文 / 清理台账 + 该作用域内的向量点;**不删集合**(集合是与正式共用的) |
| 拒绝「假成功」 | `MEMORY_WRITE_ENABLED=false` 时脚本**直接退出**:那时 `enqueue_extraction` 会静默返回 `None`,构建会「跑完、不报错、一条记忆也没有」 |
| 环境 | **评测要在独占环境跑**:计量事件的 `CallContext` 里没有 user_id,统计只能按 purpose + 时间窗过滤,同一时间窗内别的用户的记忆调用也会被计入(见 §6.7) |

### 6.3 数据集格式

**v1(本仓库自定义,顶层两个数组,无 `schema_version`):**

```json
{
  "name": "数据集名字(样本文件里写明是合成数据)",
  "conversations": [
    {
      "id": "c-1",
      "subject": "可选:这段会话属于谁(多主体数据集必填)",
      "turns": [
        {"user": "……", "assistant": "……"}
      ]
    }
  ],
  "questions": [
    {"id": "q1", "question": "……", "answer": "参考答案(可选)", "conversation_id": "c-1", "category": "可选的原生字段"}
  ]
}
```

规则:

- `conversations` 必填、非空;每条会话要有 `id` 与 `turns`,`turns` 至少一轮。
- 每轮的 `user` / `assistant` 都要有;构建顺序按数组顺序(记忆的时序就是数据的时序)。
- `conversations[].subject` 可选(字符串):这段会话的记忆归谁。**多主体数据集(一段会话 = 一个人)必须写** —— 不写就全归同一个缺省用户,`memory` 模式会把别人的记忆喂进这道题。主体在 run-id 派生的 user_id 上再分一层,同一 run 内 A 与 B 的记忆互相召不回。
- `questions[].id` 与 `questions[].question` 必填;`answer` / `conversation_id` / `category` 可选。`conversation_id` 对应某条会话的 `id`,决定 `full_context` 模式喂哪段历史(该会话的轮次),也决定 `memory` 模式用**哪个主体**的记忆(`subject` 跟着会话走);**缺省或对不上直接报错**(不回退到全部对话 / 缺省主体 —— 静默回退会把「喂错历史」伪装成正常结果)。
- 构建完成后 `cmd_build` 会把原数据集(含路径与内容摘要)存进 run 目录,**ask 阶段不再重读外部文件**,避免边改数据边跑评测。
- 仓库自带 `backend/scripts/memory_eval.sample.json`:**纯合成数据**,2 条会话 × 4 轮、4 个问题(其中一个是「记忆里没有,应当如实说不确定」的负样本)。它不是基准,只是冒烟用。

**v2(`schema_version: 2`,LoCoMo 适配产物,由 `prepare` 生成,不必手写):**

```json
{
  "schema_version": 2,
  "source": { "kind": "locomo", "attribution": "……", "notes": ["……"] },
  "conversations": [
    {
      "id": "locomo:conv-26", "subject": "locomo:conv-26",
      "speakers": {"a": "Caroline", "b": "Melanie"},
      "sessions": [
        {"index": 2, "date_time_raw": "1:56 pm on 8 May, 2023",
         "date_time": "2023-05-08T13:56:00", "date_time_status": "parsed",
         "turns": [{"dia_id": "D2:1", "speaker": "Caroline", "order": 1, "text": "……",
                    "img_url": "", "blip_caption": "", "query": ""}]}
      ]
    }
  ],
  "questions": [
    {"id": "locomo:conv-26:q1", "conversation_id": "locomo:conv-26", "question": "……",
     "answer": "……", "adversarial_answer": "", "category": 4, "category_name": "single-hop",
     "evidence": ["D2:1"], "evidence_raw": ["D2:1"], "evidence_unresolved": [], "evidence_status": "ok"}
  ]
}
```

v2 的约定(与 v1 的关键差异,细节见《LoCoMo 长期记忆评测操作指南》):

- **一个样本 = 一个主体**(`subject = locomo:<sample_id>`):两个说话者的记忆同属这一个用户(会话双方是同一个人生活史的一部分),不同样本之间完全隔离;不能给两个说话者分两个用户,否则「跨会话多跳」类问题会有一半证据召不回。
- 会话按 `index` **数字**排序(不做字符串序:session_2 必须早于 session_10);构建时**一个会话一个提取任务**、逐个驱动 worker,顺序落在编排层。
- 两位说话者映射为**同一个 user 角色**(不能把其中一位映射成 assistant,那等于丢掉那个人的全部表述);正文带「姓名:」前缀,随任务下发适配说明(`extract_note`)要求提取结果保留人物姓名,防止两人事实混成一人。
- 时间:原始字符串照留(`date_time_raw`),能解析时存 naive ISO(`date_time` 不带时区),状态记 `parsed / unparsable / missing` —— 不猜、不擅自赋 UTC。
- `evidence`:逐条与 dia_id 对账;打包(`"D9:1 D4:4"`)、分号、前导零(`"D02:01"`)都归一;对不上的进 `evidence_unresolved`(状态 `partial / unresolved`),坏形态(`"D"`)不炸、如实记。
- 图片:不下载、不识别;`img_url` / `blip_caption` 原样保留,历史文本以 `[分享了图片,图片描述:…]` 附在消息后。

`prepare` 的输出即 v2 数据集,`build` / `ask` 对两种格式都认。

### 6.4 怎么跑

全流程六步:`prepare → build → ask → score → report → purge`(单跑 `run` = build + ask + purge)。**`prepare`、`score`(不含 judge)、`report` 不连库、不调模型**,可以在任何机器上跑。

**先决条件**(只对 build / ask / purge 而言):`.env` 配好 MySQL / Qdrant / Redis / LLM / Embeddings,且 `MEMORY_ENABLED=true`。脚本启动前先过 `require_ready()`:**没配 MySQL、记忆功能关闭、或 `MEMORY_WRITE_ENABLED=false` 时直接退出**——最后一条最阴险:暂停写入时 `enqueue_extraction` 静默返回 `None`,构建会「跑完、不报错、一条记忆也没有」。`run-id` 也有校验(只允许字母 / 数字 / `.` `_` `-`,以字母或数字开头,最长 49 字符):它既进作用域又进目录名,不合法就是拒绝而不是猜。

**构建会产生真实付费调用**(每轮对话一次提取 + 若干次维护决策 + 每次写入的向量化)。样本数据集一次完整冒烟大概几十次调用,**量很小但不是零花费**;想完全不花钱,把 `LLM_*` / `EMBEDDINGS_*` 指向本地替身端点再跑(测试套件就是这么做的,见 §7 第 3 条)。

```sh
# 工作目录:backend/

# 0) (仅 LoCoMo 数据需要)适配原始 locomo10.json → 评测数据集;纯文件操作,零花费
python scripts/memory_eval.py prepare --input /path/to/locomo10.json \
    --output data/locomo-prepared.json --sample-limit 1     # 先只取 1 个样本

# ① 只构建:按历史顺序逐个登记任务、逐个驱动 worker 到收尾
python scripts/memory_eval.py build --dataset scripts/memory_eval.sample.json --run-id smoke-0001

# ② 只提问(产物在 data/eval/runs/smoke-0001/;不带 --answer = 不调模型生成)
python scripts/memory_eval.py ask --run-id smoke-0001

# 要真实回答(每个问题 × 每个模式一次聊天调用):
python scripts/memory_eval.py ask --run-id smoke-0001 --answer

# ③ 评分:默认只算本地 F1 / BLEU-1(零调用);judge 显式开启才有付费裁判调用
python scripts/memory_eval.py score --run-id smoke-0001
python scripts/memory_eval.py score --run-id smoke-0001 --metrics f1,bleu1,judge --judge-use-answer-model

# ④ 报告:汇总 report.json + report.md(纯本地)
python scripts/memory_eval.py report --run-id smoke-0001

# ⑤ 一条龙:build + ask(--keep 留下数据人工看;不加 = 跑完自动清理)
python scripts/memory_eval.py run --dataset scripts/memory_eval.sample.json --run-id smoke-0002 --keep

# ⑥ 只清理(比如 ⑤ 忘了 --keep 想再看数据,或中途失败)
python scripts/memory_eval.py purge --run-id smoke-0001
```

要点:

- `build` 的收尾判据分四项:队列(pending / running)、**失败任务**、待索引、清理台账;**四项全干净才算 `complete`**,否则返回码非零。顺序上按数据集的历史顺序「登记一个会话 → 驱动到该批收尾 → 再登记下一个」——同一时刻的提取与维护决策只涉及一段会话,时序落在编排层,不改正式 worker 的调度。
- **`ask` 有两道闸**:① run 目录里必须有 `build.json`,且数据集摘要与构建时一致(换了数据集不能复用旧记忆);② 构建必须 `complete`。诊断性放行要显式加 `--allow-incomplete`,结果标记 `run_valid=false` 且退出码非 0。
- 同一个 run-id 重复 build 是安全的:入队按 dedupe key 幂等,不会产生重复记忆也不会重复付费。
- `ask` 不带 `--dataset` 时用 run 目录里 `build` 留下的 `dataset.json`。
- `--modes` 可裁剪模式,如 `--modes no_memory,memory`;`--context-chars` 控制「超窗」判定的**近似**阈值(默认 24000 字符;不折算 token)。
- **ask(不含 --answer)也会产生少量真实调用**:`memory` 模式每个问题要发一次检索(一次查询向量化,可能还有一次重排),这比生成便宜得多,但不是零。
- 构建期出现**暂时性失败**(网络抖动)时,任务按退避重排,`build` 会在 `--max-ticks` 内等不到收尾而报未完成;要等退避就加 `--sleep 5` 之类,或稍后对同一 run-id 重跑 `build`(幂等,已成功的不会重做)。

### 6.5 三种模式与超窗记录

| 模式 | 喂给模型什么 | 说明 |
| --- | --- | --- |
| `no_memory` | 什么都不喂(只有统一回答指令) | 基线 |
| `memory` | 长期记忆检索块(≤ `MEMORY_CONTEXT_CHARS`,超出按预算截断并标 `trimmed`) | 与线上聊天同一条路径:双路召回 → MySQL 校验 → RRF → 重排 → top_k |
| `full_context` | 该题**所属会话**的全部历史原文 | **超过字符预算则跳过回答调用不截断**:`over_window=true` 如实记录,`truncated=false`。超窗的样本人工决定怎么处理(切分 / 换长上下文模型 / 弃用),脚本不替人做主 |

三种模式的差别**只在上下文块**:系统提示是同一份评测回答指令(`eval-answer/2`,要求依据证据简短作答、无依据说不知道、不调用任何工具),并随 `run.json` 留档 —— 不偷用聊天页的实验室提示词。每道题在 `results.json` 里留下三个模式各自的回答(开了 `--answer` 才有)、`memory` 模式的**检索证据**(每条命中:排序依据 origin、RRF 分数、两路名次、revision、是否被截断、更新时间)与降级说明、`full_context` 模式的字符数与超窗标记;单题单模式失败如实记 `error / answer_error`,**不当空答案计分**,也不拖垮其余题目(每答一题落一次盘)。

### 6.6 导出物(每个 run 目录)

| 文件 | 内容 |
| --- | --- |
| `dataset.json` | 本次使用的数据集原文 + 路径 + 内容摘要(sha256 前 16 位;**摘要与路径无关**:去掉 `_` 前缀的元数据再算),复现与一致性核对用 |
| `run.json` | **固定版本**:代码 commit + 工作区是否有未提交改动、模型名(LLM / Embeddings / Rerank)、温度、关键检索参数、模式与超窗阈值、统一回答指令版本与原文、数据集摘要、构建交叉引用,以及本次的 `scope` / `collection` / 各主体派生出的 `user_ids`(便于人工核对落在哪、清理该圈哪几个用户)。**不含任何 key** |
| `build.json` | 构建摘要:会话 / 主体数(**多主体时每个主体的派生 user_id 都列出来**)、实际入队数与已处理数、驱动轮数、`drained`、**`complete`**(队列 / 失败任务 / 待索引 / 清理台账四项全干净)、记忆条数、任务计数、`jobs_failed`、`cleanup`、适配说明版本(v2) |
| `results.json` | 每题 × 每模式的回答与证据;`full_context` 里带 `history_scope` 与字符数;每行带标准 `evidence_expected / evidence_unresolved / evidence_status`(诊断用,不算召回率);`run_valid` 与 `invalid_reason` 标记该轮是否可信;末尾附 `llm_usage`(回答调用的 token,缺用量记 unknown)与 `usage`(计量库调用统计,见下) |
| `scores.json` | 评分产物:`metrics`(本次算了哪些)、`protocol`(F1 / BLEU-1 / judge 各自的协议版本、对齐项与**偏差**)、逐题逐模式分数与 `judge` 结果、`summary`(mean 逐题 / macro 类别均分开列;失败 / 跳过 / judge_error 单独计数) |
| `report.json` / `report.md` | 汇总报告:三模式对照、分类别表、失败样本清单、证据诊断、延迟与 token 口径、局限清单 |
| `purge.json` | 清理结果:`scope` / 清了哪些 user_id、每个用户清掉的行数、清理台账收尾状态、`points_left`(本作用域残留向量数)、`clean` 与 `status` |

「固定模型 / 提示词 / 生成参数 / 代码版本」就是 `run.json` 的职责:两次评测只要 `run.json` 不一致,结果就不可比。

### 6.7 调用统计的口径与已知局限

`usage` 按 purpose(`memory_extract` / `memory_maintenance` / `memory_search`,以及既有的 `query` / `document_index`)与**构建/提问的时间窗**过滤计量事件,给出调用次数与分服务费用。局限必须讲清:

- 计量事件里**没有 user_id**(`CallContext` 不带,这是计量模块既有设计,本模块不改动它),所以过滤只能按 **purpose + 时间窗**,同一时段其他人的记忆调用会混进来。**评测要独占环境**;导出的 `usage.note` 里也写了这一条。
- **回答调用与裁判调用不经过计量库**(它们不带记忆用途),所以 `usage` **不包含**这两块;回答调用的 token 单独记在 `results.json` 的 `llm_usage`(取模型响应里的 usage,缺用量记 unknown),裁判调用记在 `scores.json` 的 `judge` 字段。任何一份都不能当作本次运行的「完整费用」。
- 超时 / 失败调用按计量模块的口径记「未知」而**不是 0**;读数时注意区分「没花钱」和「花了多少不知道」。
- 价格行没配时费用显示「无法估算」——那是配置问题,不是没花钱。

### 6.8 LoCoMo 数据(已实现)

LoCoMo(`snap-research/locomo`,ACL 2024,数据 CC BY-NC 4.0)的适配、对照与评分**已经实现**,工作流与口径见专门的《LoCoMo 长期记忆评测操作指南》。三个要点先写在这里:

- **许可与归属**:只做**独立实现的结构适配**(读它的数据格式,不复制它的代码);数据仅限非商用,产物里带出处说明(`source.attribution`)。`prepare` 的输出文件名、run 目录都不含原始数据本体以外的个人信息。
- **评分口径有偏差,数值不可与官方结果对比**:F1 与官方 `evaluation.py` 对齐(归一化顺序、类别 1 多答案、类别 3 分号前段、类别 5 拒绝表述、逐题分数平均)但**不做词干化**(不引入 nltk),`score` 的 `protocol.f1.deviations` 里逐条写明;BLEU-1 是本仓库补充指标,官方没有;judge 是显式开启的辅助信号,不冒充官方指标。
- **对齐的分只是「你的系统 vs 你自己」**:不要跨论文比数,不要声称复现 LoCoMo 官方或 Mem0 论文的结果。真实 `locomo10.json` 的端到端跑仍属未验证项(§7 第 4 条),先在配齐凭证的独占环境用 `--sample-limit 1` 小样冒烟。

### 6.9 清理再确认

`purge` 圈定范围靠**反查**,不靠脚本假设:先问 `users_in_scope('eval:<run-id>')` 这个作用域里出现过哪些用户(记忆行 / 任务行 / 清理台账三处的并集,多主体数据集有几个主体就是几个),再逐个 `service.clear_user(user_id, scope='eval:<run-id>')` —— 删记忆行 / 任务行(含 payload 里的对话正文与阶段中间产物)/ 来源关联,审计行保留但正文脱敏,代次 +1,并在同一事务里登记一条清理台账;向量按 `(user_id, 作用域, 代次上界)` 删,最后数一遍本作用域还剩几个点。**不删集合**:正式的索引点与评测点同在一个集合里,删集合等于删掉生产索引。`purge.json` 的 `clean` = 没有逐用户错误 **且** 残留点数为 0。

所以「只影响本 run」不是一句承诺,而是三层结构:派生 user_id 跑不到真实账号上、`scope` 让删除条件本身写不到正式行、作用域又反查出要清的用户。

清理后可用只读 SQL 自查(把 `:prefix` 换成该 run 派生的 user_id,`scope` 换成 `eval:<run-id>`;多主体时逐个 `:prefix` 查):

```sql
SELECT COUNT(*) FROM memory_items   WHERE user_id = ':prefix' AND scope = ':scope';  -- 必须是 0
SELECT COUNT(*) FROM memory_jobs    WHERE user_id = ':prefix' AND scope = ':scope';  -- 必须是 0
SELECT COUNT(*) FROM memory_sources WHERE user_id = ':prefix' AND scope = ':scope';  -- 必须是 0
SELECT COUNT(*) FROM memory_history WHERE user_id = ':prefix'                        -- 保留:审计行数
        AND old_text IS NOT NULL;                                                    --       这条必须是 0(正文已脱敏成 NULL)
```

## 8. 回滚

| 层级 | 动作 | 影响 |
| --- | --- | --- |
| 功能级(推荐先做) | `MEMORY_ENABLED=false` 重启 | 记忆功能静默停用,数据全留;聊天与其余功能不受影响 |
| 代码级 | 回退到上一版本 | 记忆接口先报错,重启时留意旧代码对新表的兼容(旧代码根本不读这些表,安全) |
| 数据级 | 逆序执行 `0005_memory_scope_fencing_index_ops.down.sql` → `0004_memory_tables.down.sql` | **连记忆与审计一起删**(0005 的 down 只是删列删表,列里的值一并丢);Qdrant 集合需另行删除;执行前所有实例必须已下线 |
| 索引级 | 删 `MEMORY_COLLECTION` 集合 | 只丢索引,不丢记忆;重建路径见技术方案 §10 |

回滚顺序:先停量(关开关)→ 再退代码 → 最后动数据。任何一步都不要在多个实例并行写记忆时执行。


## 0006 升级与恢复补充

停止旧版应用与 Worker、备份数据库，在可弃测试库演练后再按 0004 → 0005 → 0006 升级。0006 新增审计 scope，将代次主键改为 (user_id, scope)，并使任务幂等键包含 scope。旧版程序不能与新结构混跑。

历史审计优先从仍存在的 memory_items 回填 scope；已彻底移除且没有可关联事实的旧审计无法可靠推断作用域，回填为正式作用域。升级前应清理旧评测资料，若已有此类历史需人工核对备份；不要依靠推断恢复归属。

回滚前停止 Worker，并清理评测数据（恢复旧唯一键可能因跨作用域重复任务失败），再逆序执行 0006 → 0005 → 0004。0006 回滚会删除独立评测代次并移除审计 scope，无法无损保留隔离语义。

部分提交但失败的任务会保留原始 payload 和 stages，以便检查 done/total 后恢复未完成下标。修复原因后仅重置该任务的 status、attempts、next_run_at 和租约，不要清空 stages 或 committed_at。原提取清单缺失/不合法时不能直接标成功；需人工恢复原清单或明确处理未完成事实。用户彻底清除会删除这些恢复材料。

所有迁移的 up 已于 2026-10-08 在开发库与生产库执行（见 `backend/migrations/README.md` 部署记录）；逆序回滚与真实服务联调仍属于未验证项，本轮只执行离线测试。
