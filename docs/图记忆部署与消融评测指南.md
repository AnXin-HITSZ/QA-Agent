# 图记忆部署与消融评测指南

本轮只执行离线测试，不执行真实迁移、部署或付费评测。下面的真实环境命令由运维明确选择测试目标后执行。保持旧 baseline 目录不变。

## 1. 依赖、迁移与服务

在项目根目录的 Git Bash：

```bash
conda activate qa-agent
cd backend
python -m pip install -r requirements.txt
# 先停止应用/Worker；确认连接 qa_agent_dev、已执行 0001–0008。
mysql --default-character-set=utf8mb4 -h 127.0.0.1 -u qa_migrate -p qa_agent_dev < migrations/0009_memory_graph_tables.up.sql
cd ..
```

现在 `run.sh` 已集成 Neo4j 启动，`start-dev.sh` 已集成 SSH 隧道。密码放在各环境自己的 `backend/.env`，不需要在终端 export。固定镜像为 `5.26.0-community`，不依赖 APOC 或企业版。

ECS 上先配置 `NEO4J_URI=bolt://127.0.0.1:7687`、`NEO4J_USERNAME=neo4j`、`NEO4J_PASSWORD` 和 `NEO4J_DATABASE=neo4j`，开启总开关。初次联调可保持 WRITE/SEARCH/WORKER 三个子开关关闭。先在后端所连接的数据库应用 0009，再执行：

```bash
cd ~/qa-agent
bash run.sh --deps
```

脚本读取 `.env` 的密码传给 Compose，等待健康检查（最多 180 秒），验证 Bolt 认证后才重启后端；图总开关关闭则跳过 Docker，远程 URI 不启动本机 Compose。Docker Compose 必须支持 `up --wait`。已有数据卷的密码不会因修改 `.env` 自动重置，应先使用数据库正常改密流程，再同步配置。

单独手动启动专用测试 Neo4j 的替代方式（与脚本二选一）：

```bash
read -rsp '测试 Neo4j 密码: ' NEO4J_PASSWORD
echo
export NEO4J_PASSWORD
docker compose -f docker-compose.neo4j.yml up -d
docker compose -f docker-compose.neo4j.yml ps
```

两个端口仅绑定本机，数据卷持久化。ECS 使用同一 Compose；后端运行在宿主机时使用 `bolt://127.0.0.1:7687`。若后端也容器化，应接入同一个内部 Docker 网络并使用服务名称，不把 Bolt 暴露到公网。

本地 `start-dev.sh` 会按 `NEO4J_URI` 的本地端口连接 `QA_AGENT_SSH_ALIAS`（默认 `aliyun-ecs`），转发到 ECS 的 `127.0.0.1:7687`。本地推荐使用 `bolt://127.0.0.1:7687`。端口已监听时复用，退出只关闭本次创建的隧道；不会停止 ECS Neo4j 容器。无需另开 Neo4j 隧道：

```bash
cd /d/Projects/QA-Agent
bash start-dev.sh
```

下面是无需开发启动脚本时的手动替代方式：

```bash
ssh -N -L 7687:127.0.0.1:7687 <SSH用户>@<ECS地址>
```

在 `backend/.env` 自行设置 Neo4j 连接配置和密码。这里不展示实际凭据。开发评测仍需 `APP_ENV=dev`、`qa_agent_dev` 和 `MEMORY_COLLECTION=user_memory_eval_dev`，复用原有 MySQL 隧道与 Qdrant 配置。

```ini
MEMORY_GRAPH_ENABLED=true
MEMORY_GRAPH_WRITE_ENABLED=true
MEMORY_GRAPH_SEARCH_ENABLED=false
MEMORY_GRAPH_WORKER_ENABLED=true
MEMORY_WORKER_ENABLED=true
NEO4J_URI=bolt://127.0.0.1:7687
NEO4J_USERNAME=neo4j
NEO4J_PASSWORD=<测试服务密码>
NEO4J_DATABASE=neo4j
```

修改配置后重启应用及 CLI。不同进程分别读取配置，不支持运行中热切换。

```bash
cd backend
python scripts/memory_graph.py health
python scripts/neo4j_setup.py check
cd ..
```

## 2. 构建一次

用新 run-id，不复用旧 baseline 的 scope：

```bash
export EVAL_RUN_ID="locomo-graph-$(date +%Y%m%d-%H%M%S)"
bash eval-memory.sh --action build --run-id "$EVAL_RUN_ID" \
  --dataset data/eval/datasets/locomo/locomo-one-all-questions.json
bash eval-memory.sh --action status --run-id "$EVAL_RUN_ID"
```

构建会调用真实付费提取/维护/图整理及 Embedding。图提取和图同步也必须完成，`build.json` 的 `complete` 与 `graph.clean` 都应为 true。检查失败或降级时，先修复再问答，不直接继续完整评测。

自动任务已经为新建事实生成图。现有记忆需要受控补建，可从 build.json 的 user_ids 取得对应主体：

```bash
cd backend
python scripts/memory_graph.py build --user-id '<主体UUID>' --scope "eval:$EVAL_RUN_ID"
# build 仅入队，后续 Worker 会调用模型；不会直接伪造构建成功。
cd ..
```

## 3. 固定构建，关闭图召回

停止应用/Worker，将两个写侧开关关闭，保持总开关开启：

```ini
MEMORY_GRAPH_ENABLED=true
MEMORY_GRAPH_WRITE_ENABLED=false
MEMORY_GRAPH_WORKER_ENABLED=false
MEMORY_GRAPH_SEARCH_ENABLED=false
```

重新启动 CLI。该问答进程不会连接 Neo4j，因为图召回关闭；MySQL 图事实保留。消融实验直接启动评测 CLI 即可，不必同时运行 `start-dev.sh` 的应用/Worker；隧道可在单独终端保留。

```bash
bash eval-memory.sh --action ask --run-id "$EVAL_RUN_ID" --variant nograph --context-chars 100000
bash eval-memory.sh --action score --run-id "$EVAL_RUN_ID" --variant nograph
```

默认 score 含裁判，仍会付费。仅本地词汇评分可加 `--no-judge`。每个变体保留独立结果，重跑要使用新名字。

## 4. 相同构建，开启图召回

停止当前进程，仅修改 SEARCH 并启动新 CLI：

```ini
MEMORY_GRAPH_SEARCH_ENABLED=true
```

其他模型、提示词、图事实、Qdrant、候选参数、top_k 和预算保持一致。问答不会写入记忆。

```bash
bash eval-memory.sh --action ask --run-id "$EVAL_RUN_ID" --variant graph --context-chars 100000
bash eval-memory.sh --action score --run-id "$EVAL_RUN_ID" --variant graph
bash eval-memory.sh --action compare --run-id "$EVAL_RUN_ID" --variants nograph,graph
```

产物位于 `backend/data/eval/runs/<run-id>/variants/<variant>/`，比较文件位于构建目录。固定构建摘要、代码摘要或评测条件不同会拒绝正常对比。图故障会显式降级并将有图结果标为无效。

不要改变写侧/后台开关后重新 build 两次来比较图召回，那会混入事实提取差异。旧系统 baseline 单独用于观察整体变化，不与两个固定构建变体混为同一个消融实验。

## 5. 重建、对账、修复与失败任务

管理 CLI 要明确指定 owner 与 scope。正式 scope 是空串；评测 scope 是 `eval:<run-id>`。只在掌握对应服务配置的运维终端运行，不作为匿名 HTTP 接口暴露。

```bash
cd backend
python scripts/memory_graph.py status --user-id '<主体UUID>' --scope "eval:$EVAL_RUN_ID"
python scripts/memory_graph.py reconcile --user-id '<主体UUID>' --scope "eval:$EVAL_RUN_ID"
python scripts/memory_graph.py rebuild --user-id '<主体UUID>' --scope "eval:$EVAL_RUN_ID"
python scripts/memory_graph.py repair --user-id '<主体UUID>' --scope "eval:$EVAL_RUN_ID"
python scripts/memory_graph.py retry --user-id '<主体UUID>' --scope "eval:$EVAL_RUN_ID"
```

`rebuild/repair` 只从 MySQL 图事实重建 Neo4j，不调用模型；`build` 才重新登记图整理。`retry` 将失败图任务/操作恢复为 pending，恢复 Worker 后执行。对账比较逐节点属性和边，不仅比较计数。

pending 提及需要检查来源再确认，禁止只凭同名合并：

```bash
python scripts/memory_graph.py resolve --user-id '<主体UUID>' --scope "eval:$EVAL_RUN_ID" \
  --mention-id '<提及整数ID>' --entity-id '<实体ID>'
```

确认必须在同用户/scope/generation 内；图写入关闭时先恢复写开关再确认和处理后续整理。缺实体匹配、没有路径、预算截断与 Neo4j 故障是不同情况，检查 results 中的 retrieval_trace.graph。

## 6. 清理测试数据

恢复图总开关和后台开关，保持 Neo4j 可用；不必重新开启图写入：

```ini
MEMORY_GRAPH_ENABLED=true
MEMORY_GRAPH_WORKER_ENABLED=true
MEMORY_GRAPH_WRITE_ENABLED=false
```

重新启动命令：

```bash
bash eval-memory.sh --action purge --run-id "$EVAL_RUN_ID"
# 或从 backend 执行：
python scripts/memory_graph.py purge-run --run-id "$EVAL_RUN_ID"
```

只清该构建 scope 的服务端数据，包括关联图；保留本地所有变体、评分和报告。必须检查返回 `clean=true`。Neo4j 关闭/故障时保留清理台账并返回未完成；修好连接、恢复后台后再次 purge。不能用删除 Neo4j 全库或删除共享 Qdrant 集合替代 scoped purge。

## 8. 回滚与限制

先关闭图总开关并重启，原有向量/关键词链路继续可用。关闭不会删图事实，删除请求仍记录清理意图。若需要彻底移除服务，先保持服务在线完成所有图清理，再停 Neo4j，最后备份后考虑 down 迁移。

直接执行 0009 down 会丢图权威数据。需要配套回滚代码，不能让现有图任务对着缺表运行。不要删除 Docker 持久化卷，除非明确决定销毁整个专用服务的数据。

当前实体匹配保守，不额外调用查询 LLM；缺少别名/出现代词可能不命中。图只表达已保存事实，不能代替改进事实提取召回。scope 发布持有 SQL owner 锁，并有 10,000 条有效记忆的安全上限；大规模增量投影需要后续独立设计。这些边界应在效果报告中明示。
