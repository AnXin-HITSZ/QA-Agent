# QA-Agent 调用日志与费用统计技术方案

> 记录对象:embedding(DashScope `text-embedding-v4`)与 OCR(阿里云「OCR 统一识别」)
> 两类**真实外部调用**的日志,及其**估算费用**。
> 本文与代码同源:`backend/app/metering/`(计量层)、`backend/app/api/routes/metering.py`(接口)、
> `frontend/src/components/MeteringView.vue`(页面)。文案与口径有出入时,以本文 + 代码注释为准,
> 改口径请一并改三处。

---

## 1. 范围与最终决策

| 决策 | 结论 |
|---|---|
| 日志主存储 | **MySQL**(明确不用 SQLite / Redis 当主存储) |
| Redis | 只继续做三层结果缓存 + 会话记忆(键与有效期一律不变) |
| Qdrant | 只做向量与检索元数据 |
| 统计对象 | embedding 与 OCR 的**外部调用**;**不含聊天 LLM 调用**(另账) |
| 金额性质 | 全部为**估算费用**(配置单价 × 用量),界面上不得写成「实际扣费」 |
| 官方账单 | **本期不接入**;不扣免费额度、不扣折扣、不做汇率换算 |
| 票据业务字段 | **不进 MySQL**:发票金额、报销金额等仍在 OSS 路径与检索侧,不做结构化存储 |
| 文档正文 / 图片 / 向量 | **不落 MySQL**,哪怕一列都不做 |
| 事件归属 | 业务请求 → 实际外部调用 → 缓存命中 → 估算费用,四个概念分开记、分开展示 |
| 可查询性 | 只读接口、只分页;不提供改 / 删 / 清空历史 |

### 1.1 明确不做的事

- 不记录 API Key、密码、签名 URL、原始文档正文、图片内容、用户完整查询文本;
- endpoint 只保留主机名,错误摘要统一过 `redact.safe_text`(见 `app/metering/redact.py`);
- 不改现有查询缓存策略(命中 / 未命中语义照旧),也不因计量改变缓存键与有效期;
- 不自动清理历史调用记录(保留策略见 §13);
- 不为补写日志重做任何一次已完成的 OCR / Embedding 请求(补写只重放**记录**);
- 应用进程绝不 `create_all` / 自动改表:表结构只由 `backend/migrations/` 下**手工执行的纯 SQL** 演进
  (不引迁移框架,约定见该目录 README)。

## 2. 统计口径

| 概念 | 定义 | 记在哪 |
|---|---|---|
| 业务请求 | 用户点一次「索引」/ 问一次问题 | 不在本模块(索引任务、对话各自有状态) |
| 实际外部调用 | 真正发往供应商的一次 HTTP 请求 | `call_events` 一行 = 一次真实请求 |
| 重试 | 同一次逻辑调用的第 N 次尝试 | 每次尝试各一行;`call_group` 串起同一逻辑调用,`retry_of` 指向上一次 |
| SDK 内部重试 | 供应商 SDK 自己重发的 HTTP 请求 | `call_events.http_attempts`(≥1);行数不虚增,但请求次数如实可见 |
| 缓存命中 | 复用已算过的结果,没有外部调用 | `cache_events` 一行(命中 / 未命中 / 等待复用分别计数),**不产生金额** |
| 估算费用 | 配置单价 × 计费数量,`Decimal` 精确计算 | `call_events.cost_amount`(VARCHAR→DECIMAL,可空)+ 价格快照 |
| 官方账单 | 供应商控制台的真实扣费 | **本期不接入**,界面上任何金额都不得这样描述 |

### 2.1 三条硬口径

1. **超时 ≠ 免费**。超时 / 无响应时用量未知,`usage_quantity` 与 `cost_amount` 都置空,
   `billing_status=unknown` 并给出原因,**绝不记 0**。
2. **用量优先取供应商回报**(`usage_source=vendor_response`);拿不到才退回本端计数
   (`local_count`,如 OCR 的按请求 / 按页);再拿不到就是 `unknown`。
   **绝不按字数折算 token**。
3. **不合并**:不同币种、不同用量单位**不能相加**。汇总接口按
   (服务, 币种)/(服务, 单位)分列返回,前端也不给合计。

### 2.2 「估算」的确切含义

`cost_note` 恒为 `按配置单价 × 用量估算,非官方账单`(常量 `pricing.ESTIMATE_NOTE`)。
估算**不体现**:免费额度(部分 OCR 接口有每月免费次数 / 资源包抵扣)、折扣与限时优惠、
阶梯计价、汇率、供应商侧漏计或补计。因此它只用于**量级归因与异常排查**,
对账一律以供应商控制台账单为准。

## 3. 存储职责

| 存储 | 承担 | 不承担 |
|---|---|---|
| MySQL | 调用流水、按文件分摊、缓存统计、价格配置 | 文档正文、向量、图片、票据业务字段 |
| Redis | 三层结果缓存、会话 checkpointer、文件身份登记 | 调用日志主存储(仅内存队列 + 本地补写目录做故障缓冲) |
| Qdrant | 向量与检索元数据 | 日志与费用 |
| 本地磁盘 | `METERING_PENDING_DIR`:数据库不可用时的**待写目录**(非第二份可查询日志库) | 长期保存 |

删除文件、删索引任务或清理 Redis 缓存,**都不级联删除调用历史**——
表之间没有外键(§4.5),`job_id` / `document_id` / `oss_key` 只是归属线索,允许指向已不存在的对象。

## 4. 库表与关系

迁移脚本:`backend/migrations/0001_create_metering_tables.up.sql`(`.down.sql` 回滚)——
纯 SQL、由人手工执行,约定与执行方式见 `backend/migrations/README.md`。
模型:`backend/app/metering/tables.py`。两者由 `tests/test_metering_migration.py` 离线逐项比对
(列 / 类型 / 可空 / 自增 / 主键 / 唯一键 / 索引)。

约定:时间一律 UTC、`DATETIME(6)`(微秒);金额 `DECIMAL(18,8)`;用量 `DECIMAL(20,6)`;
表 `InnoDB` / `utf8mb4`;**无外键**;参数全部走 ORM / 参数化查询。

### 4.1 `call_events` —— 调用流水(一次真实外部请求一行)

| 列 | 类型 | 说明 |
|---|---|---|
| `event_id` | CHAR(32) PK | 唯一事件 id(UUID hex);幂等补写的唯一约束 |
| `occurred_at` / `created_at` | DATETIME(6) | 事件发生 / 落库时间,UTC |
| `service` / `purpose` | VARCHAR | `embedding`/`ocr`;`document_index`(索引)/`query`(检索) |
| `provider` / `target` / `endpoint` | VARCHAR | 供应商;模型名或 OCR Type;endpoint **已脱敏为纯主机名** |
| `call_group` / `attempt_no` / `retry_of` | CHAR(32)/SMALLINT/CHAR(32) | 同一逻辑调用分组、第几次尝试、上次尝试的事件 id |
| `http_attempts` | SMALLINT | 本行背后的真实 HTTP 请求次数(SDK 内部重试计入) |
| `duration_ms` / `status` | INT / VARCHAR | 耗时;`success`/`failure`(业务调用结果,**不是日志写入状态**) |
| `error_class` / `error_message` / `http_status` | VARCHAR / SMALLINT | 脱敏后的错误摘要 |
| `provider_request_id` | VARCHAR(128) | 供应商请求 id(对账线索) |
| `usage_quantity` / `usage_unit` / `usage_source` / `usage_note` | DECIMAL(20,6)? / VARCHAR | 用量;`NULL = 未取得`;单位 `token`/`request`/`page`;来源 `vendor_response`/`local_count`/`unknown` |
| `billing_quantity` / `billing_unit` / `billing_status` / `billing_note` | DECIMAL(20,6)? / VARCHAR | 计费数量(如 `1k_tokens` 会除以 1000);`billable`/`unknown` |
| `cost_amount` / `currency` / `cost_status` / `cost_note` | DECIMAL(18,8)? / CHAR(3) / VARCHAR | **估算**费用;`NULL = 无法估算`;`estimated`/`unknown` |
| `price_id` / `price_version` / `price_snapshot` | BIGINT? / VARCHAR / JSON | 事件发生时刻的**不可变价目快照**;`version` 是规则内容摘要 |
| `job_id` / `document_id` / `oss_key` / `page_no` | VARCHAR / CHAR(32) / VARCHAR(512) / INT | 归属线索(可空;检索侧调用无归属) |

索引:`(occurred_at, service)`(列表与概览主路径)、`job_id`、`document_id`、`call_group`。

### 4.2 `call_event_items` —— 批量请求 → 文件 / 页面的估算分摊

一行 = 某个事件里一个被覆盖的文件(`event_id` + `item_key` 唯一,`item_key` 是
`document_id/oss_key/page_no` 的规范化占位,使 NULL 也能进唯一约束)。
`text_count` 是分摊权重(该文件在这次请求里的文本条数),
`allocated_cost` 按文本数比例分摊、四舍五入到 8 位小数,`allocation_note` 注明「估算,非账单金额」。

**整笔金额只记在事件行一次**;分摊只是归因视图,前端也这样展示,
不会出现「多文件各自记一笔,合计翻倍」。

### 4.3 `cache_events` —— 缓存统计(与费用流水分表)

一行 = 一批缓存结果(同一调用上下文),字段:`layer`(`ocr_raw`/`ocr_text`/`embedding`)、
`purpose`、`unit`(`page`/`text`)、`hit_count`/`miss_count`/`shared_count`/`skipped_count`、
归属线索、`note`。`event_id` 唯一。**不含任何金额**——缓存命中不产生外部调用,也就没有费用可记。

### 4.4 `price_config` —— 价格配置(界面维护:只增 + 删)

| 列 | 说明 |
|---|---|
| `service` / `provider` / `target` / `unit` / `currency` | 计价维度;`target` = 模型名 / OCR Type,**空串 = 该服务 + 供应商的通用价** |
| `unit_price` | DECIMAL(18,8),注意单位(`1k_tokens` 是每千 token 的价) |
| `effective_from` | 该规则自何时生效(UTC) |
| `source` / `note` | 价格来源(**官方价格页 URL / 名称 + 核实日期**)与备注 |

唯一约束 `(service, provider, target, unit, currency, effective_from)`。
计费单位(`pricing.UNITS`):`1k_tokens`(embedding 按千 token)、`request`(OCR 按请求)、`page`(按页)。

写入口径(**只增 + 删**):在「调用与费用 → 估算依据」页面新增 / 删除(接口 `POST /prices`、
`DELETE /prices/{id}`),或直接写库(下节给出 SQL)。**不做原地修改**:改价 = 追加一条
`effective_from` 更晚的规则;重复的唯一键(同一条录两遍)→ 409。`created_at` 没有数据库
默认值(模型侧 Python 默认),手写 INSERT 必须带上,否则严格模式会报 1364。

### 4.5 关系

```
call_events 1 ── n call_event_items      (event_id;物理上无外键,逻辑上一对多)
call_events n ── 1 price_config          (逻辑引用:price_id + price_snapshot 快照,无外键)
cache_events                             (独立:只有归属线索,不与 call_events 关联)
```

无外键是**有意为之**:删除文件 / 任务 / 缓存不得级联删除调用历史(§3),
也让补写可以在事件先到、其它对象后建的情况下顺利入库。

## 5. 价格配置与估算口径

代码:`backend/app/metering/pricing.py`(规则解析与报价)、`writer.py`(事件发生时取价)。

1. **事件发生时取当时生效的规则**:同一维度里 `effective_from ≤ occurred_at` 的最新一条;
   先精确匹配 `target`,没有才退回空 `target` 的通用价。
2. **快照不可变**:命中规则后,把整条规则(`PriceRule.snapshot()`,含 `version` 摘要)写进
   `price_snapshot`。之后改价、加规则,历史事件原样保留,**不会静默重算**。
3. **缺价格 ≠ 免费**:没有匹配规则 → `cost_amount=NULL`,原因
   `未配置该服务/模型的价格,无法估算`;价格表尚未载入时原因写作「价格表未载入」,
   写出器在**价格表成功载入后**才补一次价(仍按事件发生时刻选规则),把原因改成「未配置」。
4. **缺用量 ≠ 免费**:拿不到用量 → `cost_amount=NULL`,原因「缺供应商报的用量,无法估算」。
5. **全链路 Decimal**,金额四舍五入到 8 位小数(`ROUND_HALF_UP`);绝不经过 float。
6. 价格表在内存里缓存 `METERING_PRICE_CACHE_SECONDS`(默认 60 s),业务线程**不读库**;
   改价最多滞后这么久生效。数据库故障时沿用上一次成功的表并在状态里报 `price_error`。

### 5.1 官方价格来源与核实状态

> ⚠️ **本项目不内置、不硬编码任何官方价格**:`price_config` 为空时所有金额一律显示
> 「无法估算」,这是有意的——未经核实的单价写进代码比没有价格更糟。
> 下表的数值仅供配置时参照,**必须以供应商控制台 / 官方价格页的实时价格为准**。

| 项目 | 官方来源 | 2026-10-03 查到的口径 | 核实状态 |
|---|---|---|---|
| DashScope `text-embedding-v4` | 阿里云百炼文档:「[text-embedding-v4](https://help.aliyun.com/zh/model-studio/text-embedding-v4)」「[同步接口 API 详情](https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api)」 | 按**输入 token** 计费;文档同时出现 0.5 元/百万 与 0.514 元/百万(疑似地域差异),即约 0.0005–0.000514 元/千 token;另有免费额度与限时优惠,控制台为准 | **待核实**(需在百炼控制台确认该账号所在地域的实际单价与优惠) |
| 阿里云 OCR(统一识别 `RecognizeAllText`) | 阿里云帮助中心「文字识别计费介绍」/ OCR 控制台 | **按调用次数**计费,按量付费为**阶梯价**(调用量越大单价越低),另有免费额度与资源包抵扣;仅**成功识别**计费,失败不扣费;不同 `Type`(通用文字 / 发票 / 付款详情…)单价可能不同 | **待核实**(阶梯与资源包无法用单一单价表达,见 §5.2) |

配置入口:前端「调用与费用 → 估算依据」页面(**推荐**,写入前会做同样的校验);
也可以直接执行 SQL(两条路写同一张表):

```sql

-- 单价请换成核实过的值(这里 0 只是占位);created_at 无数据库默认值,必须显式给(UTC)
INSERT INTO price_config
  (service, provider, target, unit, currency, unit_price, effective_from, source, note, created_at)
VALUES

   '2026-01-01 00:00:00',
   'https://help.aliyun.com/zh/model-studio/text-embedding-synchronous-api',
   '核实日期 2026-10-03:以控制台实时价为准;此处 0 值仅为占位,上线前必须替换',
   UTC_TIMESTAMP(6));

-- ocr:按请求,通用价(target 空串),自 2026-01-01 起生效
INSERT INTO price_config
  (service, provider, target, unit, currency, unit_price, effective_from, source, note, created_at)
VALUES
  ('ocr', 'aliyun', '', 'request', 'CNY', 0.00000000, '2026-01-01 00:00:00',
   '阿里云 OCR 计费介绍(控制台)', '阶梯价 / 资源包 / 免费额度本期不建模;取一个代表性单价用于估算',
```

删除误录条目:`DELETE FROM price_config WHERE id = <id>;`(或用页面上的删除按钮)。
删除**不会**改历史:已发生事件保留当时的 `price_snapshot` 与估算金额。

### 5.2 估算**无法体现**的计费因素(如实声明)

- **阶梯价**:OCR 按量付费随月调用量降档。`price_config` 一条规则只有一个单价,
  估算会系统性偏离实际——要么按高档位配置(偏保守),要么按当前档位配置并定期复核;
- **免费额度与资源包**:不扣减,估算会**高于**实际账单;
- **不同 Type 单价不同**:可为每个 `Type` 各配一条 `target` 精确价,未配则落通用价;
- **限时优惠 / 折扣 / 汇率**:一律不体现;
- **失败与未知**:OCR 仅成功计费,失败调用记 `billing_status=unknown` 且不计金额,
  与供应商口径一致;超时是否计费未知,同样不猜。

## 6. 缓存统计口径(三层)

复用现有缓存实现(`app/rag/ocr_cache.py`、`app/rag/embedding_cache.py`),
**不改键、不改有效期、不改命中逻辑**;只在既有函数里追加一行统计上报。

| 层 | 含义 | 命中意味着 | 单位 |
|---|---|---|---|
| `ocr_raw` | OCR 原始识别结果(按页) | 不再发起识别请求(**不花钱**) | page |
| `ocr_text` | 原始结果 → 文本的本地转换 | 不重跑转换,也不涉及外部调用 | page |
| `embedding` | 文本 → 向量 | 未命中才真的去调供应商 | text |

规则:

- **命中与外部调用分列**:命中进 `cache_events`,外部调用进 `call_events`,两边不重复计;
- **只计实际未命中**:embedding 只有未命中的那部分才产生调用事件;
- **等待复用(`shared`)与去重(`skipped`)不计外部调用**:并发下等待同一把计算锁、
  或发现别人已算完而直接复用的,都不发起请求;
- **OCR 原始命中后重跑文本转换**仍是本地行为,不算外部调用(转换命中有单独的 `shared`/`hit` 计数);
- **不给「节省金额」**:价格与命中粒度对不上(如按页计价 vs 按文本命中),只报次数。

## 7. 接口(FastAPI,前缀 `/api/v1/admin/metering`)

代码:`backend/app/api/routes/metering.py`;Schema:`backend/app/schemas/metering.py`。

| 端点 | 说明 |
|---|---|
| `GET /calls` | 分页调用日志(时间倒序)。过滤:`since`/`until`/`service`/`purpose`/`status`/`job_id`/`document_id`,`offset`/`limit`(默认 50,上限 200) |
| `GET /calls/{event_id}` | 单条详情:含按文件分摊 `items` 与 `price_snapshot`;不存在 404 |
| `GET /summary` | 概览:总量、成功/失败、未知用量/未知费用条数、`http_attempts` 合计、按服务、按天(UTC)、按(服务,单位)用量、按(服务,币种)金额、缓存三层、持久化健康 |
| `GET /prices` | 当前价目表(估算依据;为空说明未配置) |
| `POST /prices` | 新增价目(201)。**只增**:同一唯一键重复 → 409;校验(schema)失败 → 422;时间不可解析 → 400。写入后价格表缓存立即失效,不等 60 s |
| `DELETE /prices/{id}` | 删除误录价目(204);不存在 → 404。历史事件的快照与金额不受影响 |

约定:

- **时间窗**:`since`/`until` 接 ISO8601(可带偏移)或 epoch 秒;**缺省最近 7 天**;
  `until` 不含;窗口上限 366 天;非法值 400(不猜时区);返回里带实际生效的 `since`/`until`。
- **UTC 边界**:入参与返回都是 UTC;前端负责按本地时区显示。
- **聚合在 SQL 里做**(`store.py` 的 `summary` 用 `SUM`/`GROUP BY`),Python 不拉全表。
- **只分页,不导出**;查询失败 / 数据库不可用 → 503 并附脱敏原因
  (`/summary` 例外:仍返回 200,但 `error` 非空、数字不可信,避免被误读成「没有调用」)。
- 校验:非法 `service` / `status` → 400;`event_id` 超长 / 空 → 400。

### 7.1 权限控制(**现状必须如实说明**)

- 沿用既有 `/api/v1/admin/...` 前缀(与其它管理接口一致);
- **本项目后端目前没有登录态**:这段接口对任何能访问服务的人敞开。统一鉴权机制将后续
  引入(2026-10-04 决策:与其它管理接口一起做,不再维护单点令牌);
- 因此**在加上网络层限制(安全组 / 反向代理只允许受信来源)之前,不要把后端直接暴露到公网**;
- 这是一个**已知缺口**,不是「已隔离」:API 里没有任何按用户的费用归属。

历史:早期版本曾有可选的 `ADMIN_API_TOKEN` + `X-Admin-Token` 请求头,已于 2026-10-04
按决策移除,避免与即将引入的统一鉴权重复造第二套令牌体系。

### 9.1 新增环境变量(见 `backend/.env.example`)

| 变量 | 默认 | 说明 |
|---|---|---|
| `METERING_ENABLED` | `true` | 总开关;关掉后整层只做一次布尔判断 |
| `METERING_MYSQL_URL` | 空 | **留空 = 整个计量层静默关闭**(不影响 OCR / 索引 / 检索) |
| `METERING_MYSQL_POOL_SIZE` | 5 | 连接池(每 worker) |
| `METERING_MYSQL_MAX_OVERFLOW` | 5 | 溢出连接 |
| `METERING_MYSQL_POOL_RECYCLE_SECONDS` | 1800 | 连接回收(小于 MySQL `wait_timeout`) |

DSN 形如:

```
METERING_MYSQL_URL=mysql+pymysql://qa_agent:密码需URL编码@127.0.0.1:3306/qa_agent_prod?charset=utf8mb4
```

- 密码里的 `@ : / # % ? &` 等必须按 URL 编码(`@`→`%40`, `#`→`%23`, `%`→`%25`…),
  否则会被当成 DSN 结构符(这个 DSN 只被应用读取;迁移是 `mysql` 客户端执行 SQL,不读它);
- **不要修改 / 覆盖现有 `.env` 里已经填好的真实凭据、Redis 地址、OSS 地址等环境专属配置**;
  `.env.example` 只给模板;**不要把本地 `.env` 整份复制到 ECS**,按差异逐项填。

### 9.2 建库(在 ECS 的 MySQL 上执行)

先确认版本:`SELECT VERSION();`。MySQL 8.0 用 `utf8mb4_0900_ai_ci`,
5.7 用 `utf8mb4_unicode_ci`(建表未显式指定排序规则,会继承库的默认值,所以这里必须选对)。

```sql
-- 开发库与生产库分开(本方案约定两库并存:开发用 dev,生产用 prod)
CREATE DATABASE qa_agent_dev  DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE DATABASE qa_agent_prod DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

-- 迁移账号:能建 / 改表,只授权这两个库(不用 root)
CREATE USER 'qa_migrate'@'localhost' IDENTIFIED BY '<强密码>';
GRANT ALL PRIVILEGES ON qa_agent_dev.*  TO 'qa_migrate'@'localhost';
GRANT ALL PRIVILEGES ON qa_agent_prod.* TO 'qa_migrate'@'localhost';

-- 运行账号:只给 DML;连 DROP 都不需要
CREATE USER 'qa_agent'@'localhost' IDENTIFIED BY '<另一个强密码>';
GRANT SELECT, INSERT, UPDATE, DELETE ON qa_agent_dev.*  TO 'qa_agent'@'localhost';
GRANT SELECT, INSERT, UPDATE, DELETE ON qa_agent_prod.* TO 'qa_agent'@'localhost';
FLUSH PRIVILEGES;
```

主机名按部署形态改:同机直连用 `'localhost'`;后端在 Docker 里用 `'172.17.%'` 之类网段;
后端在另一台机器上就写它的固定 IP。**不要把 3306 暴露到公网**——同机 / 同 Docker 网络走内部地址,
远程情形优先内网地址或 SSH 隧道 + 安全组白名单。

### 9.3 执行迁移(在 ECS 上,用有 DDL 权限的 `qa_migrate` 账号)

迁移是 `backend/migrations/` 下的纯 SQL,用 `mysql` 客户端逐份执行:

```bash
cd /opt/qa-agent/backend/migrations      # 实际部署路径

# 开发库
mysql --default-character-set=utf8mb4 -h 127.0.0.1 -u qa_migrate -p qa_agent_dev  < 0001_create_metering_tables.up.sql
# 生产库:同一条命令换库名
mysql --default-character-set=utf8mb4 -h 127.0.0.1 -u qa_migrate -p qa_agent_prod < 0001_create_metering_tables.up.sql
```

执行完确认:

```sql
SELECT TABLE_NAME FROM information_schema.TABLES WHERE TABLE_SCHEMA = DATABASE();
-- 应恰好是这 4 张:call_events / call_event_items / cache_events / price_config
```

- 回滚:`mysql ... qa_agent_dev < 0001_create_metering_tables.down.sql` —— 会连数据一起删,线上慎用;
- MySQL 8.0 与 5.7 都能执行:建表不写 `COLLATE`,排序规则跟随 §9.2 建库时的选择;
- **先应用迁移,再让带 `METERING_MYSQL_URL` 的代码上线**:反过来在缺表期间,写入会一直失败并转入
  补写目录(§11),库补上后自动补写;
- **不要依赖应用启动自动建表**:应用永远不 `create_all`,也不引迁移框架(约定见 `migrations/README.md`);
- 迁移用 `qa_migrate` 账号,运行用 `qa_agent` 账号,两者分离;
- **本文档只写步骤,不代为执行**:建库与迁移由你在 ECS 上直接跑。

### 9.4 MySQL 侧建议

```ini
# my.cnf(按需;与后端池参数配套)

wait_timeout    = 28800          # 远大于 POOL_RECYCLE(1800),避免用到陈旧连接
```

## 10. 连接池与并发

- **每进程一个引擎**(`app/metering/db.py` 的 `get_engine()`,懒建、URL 变了才重建),
  参数:`pool_pre_ping`(陈旧连接检测)、`pool_recycle`、连接 / 读 / 写超时、`charset=utf8mb4`;
- 连接数账:`uvicorn --workers 2` × (5 + 5) = 最多 20 条,再加迁移 / 运维连接,
  远小于常见 `max_connections`;worker 调大时同步调小池;
- **会话不跨线程**:后台写出线程用 `session_scope()` 独立开会话;请求线程的查询各自开会话;
  绝不在线程之间传 Session;
- **长事务不跨外部调用**:事务只包住一次 INSERT / 一次查询,绝不在事务里等 HTTP;
- 事件入队是内存操作(`queue.put_nowait`),**不阻塞事件循环 / 请求线程**;
- 关停(lifespan exit)时 `metering.stop()`:停后台线程 → 尽力冲一次队列(冲不掉落盘)→
  `db.dispose()` 释放连接池。

## 11. 故障补写与一致性边界

链路:业务线程 `record_call()` → 进程内队列 → 后台线程批量 `INSERT` → 失败则落
`METERING_PENDING_DIR` → 数据库恢复后按退避扫描补写。

| 保障 | 实现 |
|---|---|
| 不影响业务 | `record_*` 全程 try/except,任何异常只记 warning;写库失败**不会**把已成功的 OCR / Embedding 变成失败,更不会触发重试 |
| 不重做付费调用 | 补写只重放「记录」,数据源头是 `call_events` / `cache_events` 的 payload,从不回供应商 |
| 幂等 | `event_id` 主键 + `ON DUPLICATE KEY UPDATE`(重复行 rowcount=0,计数只认新插入行);补写可以安全重复 |
| 多 worker 安全 | 补写目录的领取是**原子重命名**(`pending.claim` → `*.claimed`,多进程只有一个成功);陈旧领取有 `sweep_stale_claims()` 回收 |
| 提交后再删 | 只有数据库事务提交成功才 `pending.finish()` 删除补写文件 |
| 不敲打故障库 | 指数退避(5 s → 最大 300 s);人工 `flush()` 不受退避限制 |
| 资源上限 | 队列 `METERING_QUEUE_MAX`、批 `METERING_FLUSH_BATCH`、磁盘按事件数自然增长 |
| 不静默丢 | 连补写文件都写不下(磁盘故障)才计 `lost` 并 `logger.error`;`/summary.persistence.lost > 0` 与前端警示都会暴露 |
| 启动不阻塞 | 后台线程懒启动,首连失败只影响日志,不影响服务可用 |

**承认的窗口(不承诺严格一次)**:

1. 进程在「付款调用已成功、事件还没入队」之间崩溃 → **该次调用无记录**;
2. 进程在入队后、落盘前被 `kill -9`(队列是内存) → 同上;正常关停会冲刷,落不下就落盘;
3. 数据库提交成功但 `pending.finish()` 前崩溃 → 补写文件重放一次,**幂等吸收,不重复计数**;
4. 供应商侧「已受理但客户端超时」这类调用:客户端记 `unknown`,供应商账单可能仍计费——
   对账差异属于**信息本身不可得**,不是丢记录。

补写与业务失败是两回事:业务失败(`status=failure`)照常记录并有金额/未知口径;
日志补写失败只影响**记录完整性**,前端分开展示。

## 13. 备份、保留与恢复

- **备份**:`call_events` / `call_event_items` / `cache_events` / `price_config` 与普通业务表同策,
  纳入 MySQL 例行 `mysqldump` / 云备份;`price_config` 体量小,建议单独导出留档
  (它是历史估算的**解释依据**,丢了就无法复现旧金额的解释);
- **恢复**:先恢复库,再起后端;积压在 `METERING_PENDING_DIR` 的记录会在下一轮自动补写
  (幂等,不会与恢复的数据重复计数);
- **保留**:**不自动清理**。需要归档 / 清理时,建议按 `occurred_at` 分区或导出后人工删除,
  并先确认「调用历史即审计线索」的业务要求;删除是不可逆的;
- **删除业务对象不删日志**:删文件 / 删任务 / 清缓存都不动这四张表(§4.5)。

## 14. 已知限制与未验证项

1. **权限未隔离**:没有登录态,接口只靠网络层限制(§7.1;统一鉴权机制后续引入);
2. **未接入官方账单**:不扣免费额度 / 折扣,不做汇率与对账;金额仅供量级参考;
3. **阶梯价 / 资源包无法建模**:单一单价对 OCR 阶梯计费只能近似(§5.2);
4. **崩溃窗口**:极端情况下可能丢记录(§11),`lost` / `pending` 会暴露;
5. **价格生效滞后**:改价最多滞后 `METERING_PRICE_CACHE_SECONDS`(默认 60 s);
6. **不含聊天 LLM**:对话 token 消耗不在本期范围;
7. **MySQL 集成测试在无测试库的环境下未验证**:SQLite 结果不作为 MySQL 承诺,
   交付时如实标注(§12);
8. **`ocr_text` 层按页统计**:文本转换的粒度是页,与 embedding 的条数粒度不同,两者不可加总。
