# QA-Agent 认证、鉴权与用户管理技术方案

> 记录对象:**登录 / 注册 / 审批 / 会话 / 权限**六件事,以及它们如何改造原来的「无登录态」服务。
> 本文与代码同源:`backend/app/auth/`(认证层)、`backend/app/conversations/`(会话目录)、
> `backend/app/api/routes/{auth,admin_users,conversations}.py`(接口)、

> `frontend/src/components/auth/`(前端)。
> 文案与口径有出入时,以本文 + 代码注释为准;改口径请一并改两处。

## 1. 范围与最终决策

| 决策 | 结论 |
|---|---|
| 身份数据主存储 | **MySQL**(与调用日志同库:`MYSQL_URL`) |
| Redis | 只继续做待办存储、结果缓存、**对话记忆**(角色不变) |
| access token | **JWT(HS256)**,15 分钟;**只放在前端内存**,不进 localStorage / URL / cookie |
| refresh token | 高熵随机串(384 位),**HttpOnly cookie**,只存 SHA-256 摘要入库,轮换 + 重放检测 |
| CSRF 防护 | 双提交(`X-CSRF-Token` = `qa_csrf` cookie);+ `SameSite=Lax` + 固定 Path |
| 密码哈希 | **Argon2id**(64 MiB / 3 轮 / 4 路),NFC 归一化,8–128 字符,**绝不截断** |
| 邮箱 | 去空白 + 整体小写 + **保留句点与 +标签**;列显式 `COLLATE utf8mb4_bin` |
| 角色 | 两个:`user` / `admin`。**没有**「注册成管理员」的路径 |
| 首管理员 | 只能由服务端 CLI 建(`python -m scripts.create_admin`),密码 getpass 交互输入 |
| 发信 | 阿里云邮件推送的 SMTP 通道;**服务地址按自己账号的控制台填**,不猜、不照抄示例 |
| 危险动作 | 改密 / 重置 / 停用 / 退出全部设备 → 撤销全部会话 + 递增 `auth_version`(立即生效) |
| 迁移 | 手写编号 SQL(0003),**不引迁移框架**;应用进程绝不 `create_all` |
| 前端 | 沿用现有 hash 路由(不引 vue-router);新增 `stores/auth.ts` 作**唯一请求出口** |

### 1.1 明确不做的事

- **不发真实邮件**(测试用 FakeMailer;本地演练用 `MAIL_PROVIDER=fake`),不建真实管理员;
- 不记录密码、令牌原文、邮件里的令牌到日志或审计表(令牌只存摘要);
- 不改现有 `.env` 里的真实凭据,不动 OSS / Redis / Qdrant 的任何配置;
- 不引入第二套认证机制(没有自签 cookie、没有 Basic Auth、没有「内部接口免鉴权」的后门);
- **不靠提示词约束权限**:Agent 工具按**身份**判断,不按 system prompt 里的措辞;
- 不做无限会话:refresh 轮换但**会话绝对有效期不顺延**(`AUTH_REFRESH_TOKEN_DAYS` 到点即失效);
- 不因认证改任何业务口径(计量单位、估算金额、检索行为一律照旧)。

## 2. 威胁模型与信任边界

| 威胁 | 对策 | 落在哪 |
|---|---|---|
| 令牌被 XSS 偷走 | access 只在内存;refresh 是 HttpOnly,JS 读不到 | `frontend/src/stores/auth.ts` |
| 令牌进日志 / Referer | 令牌只走 Authorization 头;邮件链接的令牌放 **hash**(不发往服务器) | `deps.py`、`lib/route.ts` |
| CSRF(靠 cookie 认证的接口) | 双提交 + `SameSite=Lax` + `Path=/api/v1/auth` | `routes/auth.py::_require_csrf` |
| 暴力破解 / 撞库 | Redis 固定窗口限流(IP + 邮箱两路);**Redis 挂了失败关闭(503)** | `app/auth/ratelimit.py` |
| 账号枚举 | 注册 / 找回一律**中性文案**;登录先验密码再谈状态;不存在的账号也跑一次同代价校验 | `service.py::_login_sync`、`passwords.dummy_verify` |
| 会话重放 | refresh 单次消费;重放 → 撤销该会话 + 审计 `rotated_replay` | `service._refresh_sync` |
| 越权读别人的对话 | 归属判定在 **MySQL 行**上(`conversations.user_id`),他人 / 不存在一律同一个 404 | `routes/conversations.py::_not_found` |
| 未授权写内容 | 参数化 SQL + 路由级守卫;前端隐藏按钮只是礼貌 | §6 |
| 库里被读走密码 | Argon2id 盐化哈希,不可逆 | `passwords.py` |
| 库里被读走令牌 | 只存摘要,比对靠**按摘要查行**(天然恒定时间) | `tokens.py` |

**信任边界**:能登上服务器(或能改 `.env` / 跑 CLI)的人 = 能造管理员的人。这正是我们要的 ——
公共注册接口只发 `role=user`,系统里**没有**第二个变成管理员的入口。

## 3. 状态机与身份

### 3.1 注册 → 可用(users.status)

```
注册 ──► pending_email ──(点邮件链接验证)──► pending_approval ──(管理员通过)──► active
                  │                                  │
                  └──────────(管理员拒绝)────────────┴──► rejected ──(管理员改判通过)──► active
                                                                     active ──(管理员停用)──► disabled ──(启用)──► active
```

三条硬规则:

1. **邮箱验证 ≠ 审批**:两件事各有各的语义,验证只写 `email_verified_at`,不动审批状态;
   审批也不顺带替你验证邮箱。
2. **只有 `active` + 已验证才发凭证**:其余状态一律 403,`code = account_{status}`,
   且这条信息**只在密码正确之后**才给(否则就成了免费的账号状态探测器)。
3. **审批是原子 CAS**(`store.set_review` / `set_user_status`):两个管理员同时点,抢输的一方
   拿 409 而不是静默覆盖。

停用 / 禁用立即生效:撤销该用户全部会话 + `auth_version += 1` → 在途的 access token 下一次
请求就撞上版本不符(不等它过期)。

### 3.2 身份快照(Principal)

`Principal{user_id, email, display_name, role, status, auth_version, session_id}` 是每个请求的
身份对象。待办的 `created_by` / `updated_by` 与审计的 `actor_user_id` 都取它 —— 存的是
**动作发生那一刻**的快照,事后改显示名不会追改历史记录。

### 3.3 首个管理员(§8 有完整步骤)

`backend/scripts/create_admin.py`,只在命令行可用:

```bash
cd backend && python -m scripts.create_admin --email admin@example.com --name 张老师
# 密码走终端交互(不回显);自动化场景用 --password-stdin
```

为什么长这样:

- 密码**不走命令行参数**(`--password xxx` 会留在 shell 历史 / 进程列表 / systemd 日志里);
- 管理员没有弱口令豁免(同一个 `check_password`);
- 邮箱视为已验证(操作者当面确认过),否则首次登录会卡在「先收验证邮件」,而那时发信可能还没配好;
- 已存在同名邮箱 → **拒绝执行**(EXIT_ALREADY_EXISTS),不改密码、不覆盖 —— 改密码是另一件事;
- 一律记审计(`bootstrap_admin`)。

## 4. 邮箱与密码规则

### 4.1 邮箱规范化(`app/auth/emails.py`)

注册、登录、找回、唯一键四处**必须**调同一个 `normalize_email`:

1. 去掉首尾空白(含全角空格等 Unicode 空白);
2. **整体小写**(域名不敏感是共识;用户名部分我们也统一小写,规则简单且四处一致);
3. **保留**用户名里的句点与 `+` 标签:`a.b+lab@x.com` 与 `ab@x.com` 是两个人,绝不合并;
4. 不认 IDN、不做别名展开;域名按 LDH 字面校验;长度上限 254(用户名部分 64);
5. 唯一键与查询按**精确字符串**判定:`users.email` 显式 `COLLATE utf8mb4_bin`。
   库默认的 `utf8mb4_0900_ai_ci` 不区分重音,会把 `é@x.com` / `e@x.com` 判成同一地址而
   **意外合并两个账号** —— 这是必须显式声明排序规则的原因;
6. 主键是 UUID(36 位),邮箱不是主键,结构上给「日后可改邮箱」留了路。

格式校验只排除「确实不像邮箱」的串,不试图完整实现 RFC 5322 —— **真正确认邮箱有效性的是验证邮件那一步**。

### 4.2 密码策略(`app/auth/passwords.py`)

- 长度 **8–128 个字符**(按 Unicode 码点计),允许任意字符(空格 / 中文 / emoji);
- **不做**大小写数字符号的组合要求(NIST 800-63B 取向:长度比组合更重要);
- 先做 **NFC 归一化**再哈希(同一密码在不同输入法下必须得到同一个哈希);
- 超长**直接拒绝,绝不静默截断**(截断会让「密码后 100 位」毫无意义);
- 哈希参数写在 Argon2 编码串里,日后调参时旧哈希仍可验证,登录成功后按需 `needs_rehash` 重哈希。

> `check_password()`(不合格抛异常)与 `validate_password()`(返回错误串)看着像一对,
> **入口一律用前者** —— 后者忘记看返回值就等于放行。建管理员脚本当年就踩过这个坑。

## 5. 令牌、Cookie、CSRF 与限流

### 5.1 两类令牌,绝不混用

| | access token | refresh token |
|---|---|---|
| 形态 | JWT(HS256) | `secrets.token_urlsafe(48)`(≈384 位) |
| 存放 | **前端内存**(模块变量) | HttpOnly cookie(`qa_refresh`),前端读不到 |
| 库里 | 不存 | 只存 **SHA-256 摘要**(`auth_refresh_tokens.token_hash`) |
| 时效 | 15 分钟(`AUTH_ACCESS_TOKEN_MINUTES`) | 会话绝对有效期 30 天(`AUTH_REFRESH_TOKEN_DAYS`),**不顺延** |
| 轮换 | 每次刷新重签 | 每次刷新换新一枚,旧的记 `consumed_at` |

access JWT 的 claims 固定为 `sub / sid / ver / iss / aud / iat / exp`(另带 `typ=access`、`jti`):

- 算法**写死 HS256**,校验时只接受 HS256 —— 绝不从 token 头里取 `alg`;
- `iss` / `aud` / `exp` / `iat` 全部校验,`iat` 用的时间戳按 UTC 解释(朴素时间按本机时区
  换算会让令牌凭空早 8 小时,而且只在非 UTC 机器上现形);
- **JWT 只承载身份指针**:每次请求仍回库核对用户状态、会话是否被撤销、`auth_version` 是否匹配
  (见 `deps.current_user`)。所以撤销能**立即**生效,不用等令牌过期;
- 密钥短于 32 字节或命中示例值(`change-me` 之类)→ 拒绝签发,且启动自检就报错。

**刷新轮换与并发宽限**(`service._refresh_sync`):

```
取 refresh 行(FOR UPDATE 串行化)
├─ 未消费 ──────────────► 正常轮换:旧行记 consumed_at,发新 access + 新 refresh
├─ 已消费,且 age ≤ 宽限 ─► 判为前端并发(多个标签页撞在一起):再发一枚,会话**不撤销**
└─ 已消费,超出宽限 ─────► 视为重放:撤销整个会话 + 审计 rotated_replay → 401
```

宽限窗口是 `AUTH_REFRESH_GRACE_SECONDS`(默认 30 秒)。**并发刷新只发一次**也是前端的责任:
`refreshSession()` 做 single-flight,多处同时撞 401 共用同一个 Promise。

### 5.2 refresh cookie

- `HttpOnly`(JS 读不到)、`SameSite=Lax`、`Path=/api/v1/auth`(只有认证接口能收到它)、
  `Secure` 由 `AUTH_COOKIE_SECURE` 控制(**本地 http 开发必须 false**,否则浏览器不回收;
  **生产 HTTPS 必须 true**);
- 域默认跟随请求主机;只有跨子域才填 `AUTH_COOKIE_DOMAIN`;
- 登出(当前 / 全部)、改密、重置、停用时后端都会清 cookie。

### 5.3 CSRF(双提交)

本应用里**唯一**靠 cookie 认证的接口是 `POST /auth/refresh`(其余接口都认 Authorization 头),
所以 CSRF 校验只加在它身上:请求要带 `X-CSRF-Token`,其值必须与 `qa_csrf` cookie 一致
(常量时间比较)。缺失 → 403 `csrf_missing`;不一致 → 403 `csrf_mismatch`。
两种情况分开编码,是因为**前端能自愈的只有前者**:cookie 被浏览器策略拦掉 / 用户清过,
前端就向 `/auth/csrf` 重新取一枚再试一次(只重试一次,失败即回登录页);失配则是可疑请求,不重试。

靠 Bearer 认证的接口天然不受 CSRF 影响(Bearer 不是浏览器自动带上的凭据)——
这正是 `logout` 系列走 Bearer 而不是走 cookie 的原因:少一个能被打的洞。

`GET /api/v1/auth/csrf` 是**预取**:只发一枚 cookie,不做任何敏感操作 ——
邮件链接里的 `GET`(页面加载)也就不会误触发验证(「GET 预取不得执行敏感操作」)。

### 5.4 限流(Redis 固定窗口,失败关闭)

| 动作 | 键 | 额度 |
|---|---|---|
| 注册 | `register:ip:{ip}` / `register:email:{邮箱}` | 10 / 5min · 3 / 1h |
| 登录 | `login:ip:{ip}` / `login:email:{邮箱}` | 30 / 5min · 10 / 5min |
| 刷新 | `refresh:ip:{ip}` | 60 / 5min |
| 取 CSRF | `csrf:ip:{ip}` | 60 / 5min |
| 验证邮箱 | `verify:ip:{ip}` | 30 / 5min |
| 重发验证 | `resend:ip:{ip}` | 10 / 5min |
| 改密 | `pwdchange:ip:{ip}` | 10 / 5min |
| 找回密码 | `forgot:ip:{ip}` / `forgot:email:{邮箱}` | 10 / 5min · 3 / 1h |
| 重置密码 | `reset:ip:{ip}` | 10 / 5min |

- **Redis 不可用 = 失败关闭**(503 `rate_limit_unavailable`),不放开限制 ——
  否则正好在 Redis 出问题的时候给暴力破解开了门;
- 计数放 Redis 而不是进程内存:多 worker / 多副本下内存计数等于没做;
- `AUTH_RATE_LIMIT_ENABLED=false` 只用于本地开发,线上不许关。

### 5.5 客户端 IP

`AUTH_TRUSTED_PROXY_COUNT` 决定是否采信 `X-Forwarded-For`(从右往左数第 N 个)。
默认 **0 = 谁都不信**,直接用 TCP 对端地址 —— 客户端可以伪造 XFF,拿它做审计 / 限流等于没做。

## 6. 权限矩阵(与 `tests/test_auth_rbac.py` 同步)

| 接口 | 级别 | 说明 |
|---|---|---|
| `GET /health` | public | 健康检查 |
| `/auth/register`、`/auth/verify-email`、`/auth/verify-email/resend`、`/auth/login`、`/auth/refresh`、`/auth/csrf`、`/auth/password/forgot`、`/auth/password/reset` | public | 认证入口;**public ≠ 不设防**(仍有限流 / CSRF / 中性文案) |
| `POST /auth/logout`、`/auth/logout-all`、`GET /auth/me`、`POST /auth/password/change`、`GET /auth/sessions`、`DELETE /auth/sessions/{id}` | user | 自己的账号;`sessions/{id}` 只能撤自己的会话(别人的 → 404) |
| `POST /chat`、`POST /chat/stream` | user | 对话(SSE 也用 Authorization 头,URL 里**没有**令牌) |
| `GET /conversations`、`GET /conversations/{thread_id}`、`DELETE /conversations/{thread_id}` | user | **只看得到自己的**;他人 / 不存在 / 正在删 → 同一个 404 |
| `GET /knowledge/tree`、`GET /knowledge/download`、`GET /sops`、`GET /sops/{id}`、`GET /sops/images/{id}`、`GET /todos` | user | 只读:知识库浏览 / 下载原件、SOP 浏览、待办查看 |
| `POST /knowledge/folder`、`POST /knowledge/upload`、`DELETE /knowledge/object`、`DELETE /knowledge/folder` | admin | 知识库写 |
| `POST /sops`、`PUT /sops/{id}`、`DELETE /sops/{id}`、`POST /sops/images`、`POST /admin/sops/reload` | admin | SOP 写 |
| `POST /todos`、`PATCH /todos/{id}`、`DELETE /todos/{id}` | admin | 待办写(全局共享一份,读对所有登录用户开放) |
| `/admin/users`(列表)、`/users/{id}/{approve,reject,disable,enable,role}`、`/admin/audit` | admin | 用户管理 |
| `/admin/metering/*` | admin | 调用日志与费用(全局账) |

三条不变量:

1. **每条路由必须恰好声明一个访问级别**(`require_user` / `require_admin` / `public_endpoint`)——
   结构用例会遍历路由表逐个检查;忘了加守卫会**当场失败**,而不是等有人发现「这个接口谁都能调」;
2. **前端隐藏按钮 ≠ 授权**:界面只是礼貌,真正的门在依赖上;
3. **管理员默认也只看自己的会话**:别人的会话对管理员同样是 404 —— 用户管理看的是账号,不是内容。

管理员能做的事里,**唯一不能做的是动自己**:停用自己 / 改自己的角色会被后端拒绝
(`不能停用自己的账号` / `不能修改自己的角色`),免得唯一的 admin 自锁在门外。前端也不给这几个按钮。

## 7. 存储、事务与一致性

### 7.1 六张表(0003)

| 表 | 职责 | 要点 |
|---|---|---|
| `users` | 账号 | `email` **唯一 + `COLLATE utf8mb4_bin`**;`auth_version` 每次「改密 / 重置 / 停用 / 退出全部」+1 |
| `auth_sessions` | 登录会话(设备) | `revoked_at` + `revoked_reason`;绝对有效期不顺延 |
| `auth_refresh_tokens` | 刷新令牌 | 只存 `CHAR(64)` 摘要;`consumed_at` 支持轮换与重放判定 |
| `email_tokens` | 邮箱验证 / 重置令牌 | 一次性:`purpose` + `expires_at` + `consumed_at` |
| `conversations` | 会话**目录**与归属 | `thread_id` 唯一(`VARCHAR(160)`);`status` active/deleting/deleted |
| `auth_audit` | 审计 | 谁、对谁、什么时候、什么结果、什么 IP |

三件**不随迁移种下**的东西:任何账号 / 密码哈希、任何价格行、「给旧会话补目录行」。
理由见 `backend/migrations/README.md`。

### 7.2 存储分工

- **MySQL** = 身份、授权与目录(谁是管理员、这个会话归谁、审计算据);
- **Redis** = 对话正文(checkpointer)+ 待办 + 缓存。**checkpoint 不设 TTL**:历史对话的保留
  取决于用户是否删除,不靠过期悄悄抹掉;
- 归属判定只看 MySQL 行,**绝不解析线程 id 字符串**(那玩意客户端能自己拼)。

### 7.3 线程 id

```
qa:{env}:chat:v1:u:{user_id}:c:{conversation_id}
```

- `env` 区分环境(见 `conversations/store.py`),避免测试 / 生产串线;
- `parse_thread_id()` 只用来**反向核对**,授权一律回 MySQL 查 `user_id`;
- 对外接口里的 `thread_id` 与库里的行一一对应,`thread_id` 列有唯一键(真库上验过)。

### 7.4 删除状态机

```
active ──(DELETE,原子置)──► deleting ──(Redis adelete_thread 成功)──► deleted(墓碑)
                                 │
                                 └─ 中途失败:行留在 deleting,启动对账补删
                                    (reconcile_deleting,超过 60 秒视为上次没删完)
```

- 顺序**只能是**「先标记 → 再抹 Redis → 再落墓碑」,绝不「先删 Redis 再发现库里没删掉」,
  也绝不谎报成功(Redis 抹除失败 → 503,并明确说「仍在删除中」);
- `deleting` 的行对外一律 404(与「别人的会话」同一个 404,不区分)。

### 7.5 事务与事件循环

- 每个 service 方法一个**短事务**,事务里**只碰数据库**;发信(慢、可能失败)一律放到事务**之后**;
- **数据库操作不得阻塞事件循环**:所有同步 DB 调用都经 `db.run(...)` 丢进线程池
  (`app/auth/db.py` 的同一套约定,与计量层一致);
- 连接池 `NullPool` 仅用于测试;生产用默认池 + `pool_pre_ping`;
- worker 启动**不做 DDL**:表只由 `migrations/` 里手写的 SQL 建立。

**`.env` 写法约定(踩过的坑)**:注释**单独一行**,别写在等号后面。
`KEY=   # 说明`(空值 + 行内注释)在 python-dotenv / pydantic-settings 下解析出来的值就是
`# 说明` 这一串 —— 「留空 = 默认行为」的键会带着一段中文注释上路(`AUTH_COOKIE_DOMAIN` 变成
非法 cookie 域 → 登录态存不下;`MAIL_*` 变成注释文本 → 发信报「不认识的 MAIL_PROVIDER」)。
有值的行(`KEY=abc # 说明`)不受影响。启动时会**点名告警**这类键(`config.Settings` 的
`_warn_comment_like_values`),只报不改 —— 自动清洗会悄悄改掉真的以 `#` 开头的密钥。

**配置缺失时的表现**(一条都不能含糊):

| 缺什么 | 表现 |
|---|---|
| 数据库 | 认证接口 **503**,启动日志明确说缺 `MYSQL_URL` |
| 签名密钥(空/过弱) | 认证接口 **503**,启动自检直接失败 |
| 发信配置 | 注册 / 找回 **503**,说明缺哪几项;**不假装发过信** |
| Redis(限流) | 认证接口 **503**,失败关闭 |

**绝不降级为匿名放行**:聊天等公开能力不受影响,但认证相关的接口宁可不可用,也不敞开。

## 11. 发信(阿里云邮件推送的 SMTP 通道)

- 触发式邮件只有两类:**邮箱验证**(注册 / 重发)与**重置密码**;
- 模板纯文本,链接形如 `{AUTH_FRONTEND_BASE_URL}/verify-email?token=…` 与
  `/reset-password?token=…`;前端首屏把路径**搬进 hash**(令牌不进 nginx / 代理的访问日志);
- 邮件里**只有一次性令牌**,没有密码、没有 access token、没有用户名之外的身份信息;
- 发信在事务**之后**做;发信失败不回滚账号(注册仍成功,用户可重发);
- 配置缺失 / 半套配置 → 发信时 `MailNotConfigured`,注册 / 找回明确 **503** 并点名缺哪几项,
  绝不假装发过信、也绝不把令牌回显给客户端。

### 11.1 通道与配置(`MAIL_PROVIDER`)

DirectMail 既提供 HTTP API 也提供 SMTP 接入。**本项目只实现了 SMTP 一条**
(`MAIL_PROVIDER=smtp`,标准库 `smtplib`,不引第三方 SDK):

| 配置项 | 说明 |
|---|---|
| `MAIL_PROVIDER` | `smtp` / `fake`;留空 = 未配置(注册 / 找回明确报 503) |
| `MAIL_SMTP_HOST` | 例 `smtpdm.aliyuncs.com` —— 按账号控制台确认,不照抄示例 |
| `MAIL_SMTP_PORT` | 默认 465(隐式 TLS) |
| `MAIL_SMTP_USERNAME` / `MAIL_SMTP_FROM` | 都是**裸地址**(例 `noreply@mail.example.com`) |
| `MAIL_SMTP_PASSWORD` | 控制台给「发信地址」设的 **SMTP 密码**,与 RAM 的 AK/SK 是两回事 |
| `MAIL_FROM_ALIAS` | 收件人看到的显示名(与发信地址分开配) |

**半套配置不放过**:缺项会在首次发信时报错并逐个点名,不安静地不发信(用例
`test_mailer_must_be_configured_explicitly`)。

**SMTP 通道的传输安全**(`app/auth/mailer.py` 的 `SmtpMailer`):

- 465 = 隐式 TLS(`SMTP_SSL`);**其它端口必须 STARTTLS**,服务器不支持就直接判失败 ——
  绝不把账号口令明文递出去(用例 `test_smtp_refuses_to_send_credentials_when_starttls_unsupported`);
- `login()` 只在 TLS 建立之后调用(用例断言了调用顺序);
- 证书走 `ssl.create_default_context()`:校验证书与主机名,**不提供**「跳过验证」的开关;
- 正文一律 base64、中文头按 RFC 2047 编码 → 整封信是 7bit 纯 ASCII,不要求服务器支持
  8BITMIME / SMTPUTF8(用例 `test_smtp_message_is_pure_ascii_and_round_trips`);
- 一封一连接,不做连接池;`smtplib` 是阻塞 IO,整体在线程池里跑,不占住事件循环。

`MAIL_PROVIDER=fake` 只用于测试与本地演练(邮件留在内存里,不触网)。**本地演练时令牌从哪来**:
`APP_ENV` 为 `dev` / `local` / `test` 时,`service._log_dev_link` 会把验证 / 重置链接打进日志;
其它环境(含没写清的)一律不打 —— 日志里的令牌就是明文凭证。

**控制台核对项(必须按自己账号的控制台填,不要照抄示例)**:

1. 发信域名已在邮件推送控制台**验证通过**(DNS 的 SPF / MX / CNAME 记录齐全);
2. 发信地址 `noreply@<你的发信域名>` 已创建且状态正常;
3. `MAIL_SMTP_HOST` 用控制台「发信地址」页给的 SMTP 服务地址 —— **未知的不要猜**,
   填错的表现是连接失败 / 证书不匹配;
4. SMTP 密码在控制台给发信地址单独设置,与 RAM 的 AK/SK 无关(本项目也不再支持 AK/SK 发信);
5. 发信量 / 速率限制按账号配额核对(批量发信要走模板与收件人列表,本期不做)。

## 12. 接口一览与错误约定

### 12.1 认证(前缀 `/api/v1/auth`)

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/register` | 中性回复;发验证邮件;重复邮箱不重发 |
| POST | `/verify-email` | 消费一次性令牌 → 写 `email_verified_at`(不动审批状态) |
| POST | `/verify-email/resend` | 中性回复 |
| POST | `/login` | 成功:access token(响应体)+ refresh(cookie)。状态不对 → 403 `account_*` |
| POST | `/refresh` | 轮换;**唯一需要 CSRF 头的接口**;重放 → 401 并撤销会话 |
| GET | `/csrf` | 预取 CSRF cookie(无副作用) |
| POST | `/logout` | 撤销当前会话 |
| POST | `/logout-all` | 撤销全部会话 + `auth_version += 1` |
| GET | `/me` | 当前账号 |
| POST | `/password/change` | 校验当前密码 → 换哈希 + 撤销**全部**会话(含本次) |

| POST | `/password/reset` | 消费令牌 → 换密码 + 撤销全部会话 |
| GET | `/sessions` | 我的登录设备列表(标出 `current`) |
| DELETE | `/sessions/{session_id}` | 下线指定设备(不是自己的 → 404) |

### 12.2 管理员(`/api/v1/admin`)

`GET /users`(分页 + 状态计数)、`POST /users/{id}/approve|reject|disable|enable|role`、
`GET /audit`(可按 `target_user_id` 过滤)。

### 12.3 错误体

认证 / 管理员接口统一:

```json
{"detail": {"code": "account_pending_approval", "message": "邮箱已验证,账号正在等待管理员审批"}}
```

| HTTP | code | 含义 |
|---|---|---|
| 400 | `invalid_input`(子类 `invalid_email` / `invalid_password` / `invalid_display_name`) | 参数不合规(message 可直接展示) |
| 401 | `invalid_credentials` | 账号或密码不对(**不区分**两者;不存在的账号也跑同代价校验) |
| 401 | `invalid_token` / `token_replayed` | 令牌无效 / 刷新令牌被重放(会话已撤销) |
| 401 | `unauthorized` | 令牌缺失 / 过期 / 会话被撤 / 用户被禁用 —— 统一一条文案 |
| 403 | `account_pending_email` / `account_pending_approval` / `account_rejected` / `account_disabled` | 状态不对(**仅在密码正确之后**才给;基类码是 `account_not_usable`) |
| 403 | `forbidden` | 非管理员访问管理员接口 |
| 403 | `csrf_missing` / `csrf_mismatch` | 双提交校验失败(只有 `/auth/refresh` 会走到) |
| 404 | `conversation_not_found` / `user_not_found` | 他人 / 不存在 / 正在删 —— 同一个 404;管理员的用户接口同理 |
| 409 | `invalid_user_state` | 状态已被别人改掉(审批 CAS 抢输)、状态不允许该操作(如改非 active 账号的角色) |
| 429 | `rate_limited`(带 `Retry-After`) | 限流 |
| 503 | `auth_not_configured` / `mail_not_configured` / `mail_send_failed` / `rate_limit_unavailable` | 配置缺失 / 依赖不可用,**明确报错** |

其它业务接口仍是 `{"detail": "…"}` 字符串形状,422 仍是 FastAPI 的数组 ——
前端 `stores/auth.ts` 的 `toAuthError()` 两种都认。

## 13. 审计与安全边界

### 13.1 审计表(`auth_audit`)

记录的动作(节选):`register`、`verify_email`、`login` / `login_failed`、`refresh`、
`rotated_replay`、`logout` / `logout_all`、`password_change` / `password_reset`、
`approve` / `reject` / `disable` / `enable` / `role_change`、`bootstrap_admin`、`session_revoke`。

- 每行含:时间(UTC)、动作、结果(`ok` / `denied` / `failed`)、操作者、被操作者、邮箱、IP、备注;
- 系统动作(注册、登录、重放)的操作者为空;**系统动作与人的动作一眼可分**;
- 审批 / 停用的「撞车」(CAS 抢输)也记 `denied` —— 谁试图改、什么时候,查得到;
- **审计里绝不写密码、令牌原文、邮件链接全文**;邮箱与 IP 是审计的必要信息,按 §9.2 长期保留。

### 13.2 明确的安全边界(知道自己在哪)

- **管理员能看账号,不能看内容**:没有「读某个用户的对话」这种接口;管理员想看别人的会话
  和普通用户一样是 404。这与「管理员是实验室里可信任的人」这一前提配套 —— 如果日后要支持
  「管理员审计对话内容」,那是一个**新的、需要单独评审**的功能,不要顺手加;
- **审计可被有库权限的人改写 / 删除**:它是「操作留痕」,不是防篡改账本。真要防篡改需要
  异地日志 / 只增存储,不在本期;
- **前端拦截不是安全边界**:隐藏按钮只影响体验;所有判断在服务端;
- **JWT 无状态的部分是刻意的妥协**:撤销靠回库核对实现,代价是每请求一次 DB 查询 ——
  换来「禁用 / 改密立即生效」;
- **限流是尽力而为**:Redis 单点故障时失败关闭(宁可不可用,不给爆破开门),但分布式限流的
  精度取决于窗口实现(固定窗口有边界突刺);
- **一次性令牌的有效期是「足够短」而不是「足够安全」**:真正的保护是「单次使用 + 高熵 + 只存摘要」;
- **邮件是明文通道**:链接里的令牌谁拿到谁能用 —— 所以它只用于验证邮箱与重置密码,
  绝不用于日常认证。

### 14.1 MySQL 专属用例(默认全跳过)

```bash
# 在 ECS(或任何有测试库的地方);库名必须自证可弃,否则直接失败
export AUTH_TEST_MYSQL_URL="mysql+pymysql://user:pwd@host:3306/qa_auth_test"
python -m pytest tests/test_auth_mysql.py -q
```

三条「非真库不可」的理由:SQLite 会**静默丢弃** `FOR UPDATE`;`utf8mb4_bin` 是**列级排序规则**
(SQLite 上无法验证);SQLite **不校验 CHAR / VARCHAR 长度**(生产上踩过 1406)。
所以 SQLite 绿灯**不代表**这几条通过 —— 与 `tests/test_metering_mysql.py` 是同一种约定。
